# การจัดการคลัสเตอร์

[← ShimoDocs Suite เอกสารการติดตั้ง](../../../README.md)

## 1. ภาพรวมฟังก์ชัน

โมดูลการจัดการคลัสเตอร์เป็นคอนโซลใน MDP แพลตฟอร์มปฏิบัติการที่เชื่อมต่อกับคลัสเตอร์ของลูกค้า Kubernetes โดยมุ่งเป้าไปที่สามสถานการณ์: การตรวจสอบประจำวัน การแก้ไขปัญหาเร่งด่วน และการเปลี่ยนแปลงทรัพยากร เป้าหมายของโมดูลนี้คือเพื่อให้บุคลากรปฏิบัติการที่กำลังเวรสามารถทำงานแก้ไขปัญหาทั่วไปและงานปฏิบัติการได้โดยไม่ต้องสลับไปยังระบบเนทีฟบ่อยครั้ง `kubectl`.

ความสามารถหลัก:

- ภาพรวมคลัสเตอร์: สุขภาพของโหนด, สถานะการทำงานของแอปพลิเคชัน
- การจัดการงาน: การดู, การรีสตาร์ท, การเปลี่ยนจำนวนสำเนา, การปรับทรัพยากรของคอนเทนเนอร์, และการดู YAML สำหรับ Deployment, StatefulSet, DaemonSet, Pod, Job และ CronJob
- การจัดการการกำหนดค่า: การดู ConfigMap, HorizontalPodAutoscaler (HPA)
- ทรัพยากรเครือข่าย: การดู Service, Ingress
- การวินิจฉัยระดับ Pod: บันทึกแบบเรียลไทม์, บันทึกการล่ม K8s เหตุการณ์, เทอร์มินัลเว็บ YAML ดู

### 1.1 ผู้ใช้งานที่เกี่ยวข้อง

| บทบาท        | การดำเนินการทั่วไป                                      |
| ----------- | ---------------------------------------------------- |
| การปฏิบัติหน้าที่ | ดูความผิดปกติของโหนดและ Pod, ค้นหาบันทึก, ดูเหตุการณ์ |
| การสนับสนุนภาคสนาม | ดูสถานะสำเนาการปรับใช้, เวอร์ชันของภาพ, การร้องขอ/ข้อจำกัดของทรัพยากร         |
| เหตุฉุกเฉินของความผิดพลาด | รีสตาร์ท Deployment หรือ DaemonSet, ปรับจำนวนสำเนา, ปรับ CPU/หน่วยความจำ |
| การวางแผนความจุ | ดู HPA จำนวนสำเนาปัจจุบันและขีดจำกัดบน/ล่าง                             |

### 1.2 การดำเนินการที่ไม่แนะนำในโมดูลนี้

การลบ NAMESPACE, การบังคับไล่ Pods, การแก้ไข Secret หรือ RBAC ทรัพยากร และการดำเนินการที่ละเอียดอ่อนอื่น ๆ ไม่สามารถทำได้ในโมดูลนี้และจำเป็นต้องดำเนินการผ่านเครื่องมือเนทีฟ `kubectl` หรือเครื่องมือเปลี่ยนแปลงที่เกี่ยวข้อง การดำเนินการแบบชุดข้ามคลัสเตอร์ไม่สามารถทำได้; การดำเนินการแต่ละครั้งมีผลกับคลัสเตอร์ที่เลือกปัจจุบันเท่านั้น และ NAMESPACE. สำหรับการดาวน์โหลดบันทึกไฟล์ขนาดใหญ่ในครั้งเดียว แนะนำให้ใช้เทอร์มินัลเว็บแทนการป๊อปอัพสตรีมบันทึก

## 2. การเข้าถึงและการนำทาง

เมนูด้านซ้าย: **การจัดการการดำเนินงาน → การจัดการคลัสเตอร์**.

หลังจากเข้าสู่ระบบ, **การปรับใช้** เมนูทางซ้ายถูกเลือกโดยค่าเริ่มต้น NAMESPACE ค่าเริ่มต้นเป็นค่าแรกในกลุ่มปัจจุบัน และสามารถเลือกกลุ่มและ NAMESPACE ได้รับการสนับสนุน

## 3. งานที่ต้องทำ

### 3.1 การปรับใช้
**ขั้นตอน**: ค้นหา Deployment เป้าหมาย → คลิกไอคอนดินสอที่มุมขวาบน → จะปรากฏหน้าต่างแก้ไข → ใส่ค่าที่ใหม่ → ยืนยันการเปลี่ยนแปลง

ฟิลด์ที่รองรับการแก้ไขในป๊อปอัป: 

- จำนวนสำเนา ค่าต่ำสุด 0 ต้องเป็นจำนวนเต็ม 
- CPU คำขอ / ขีดจำกัดต่อคอนเทนเนอร์ หน่วยคือ "core" สามารถกรอกได้ `1` หรือ `1000m` 
- คำขอ / ขีดจำกัดหน่วยความจำต่อคอนเทนเนอร์ หน่วยคือ Mi สามารถกรอกได้ `512` 

หลังจากส่ง การสร้างใหม่แบบโรลลิ่งจะถูกกระตุ้น ฟิลด์ที่ไม่ได้ระบุ (image, env, probes, ฯลฯ) จะไม่ถูกเปลี่ยนแปลง 

#### 3.1.1 การรีสตาร์ท Deployment 
ขั้นตอน: ค้นหา Deployment เป้าหมาย → คลิกไอคอนลูกศรหมุนที่มุมขวาบน → ยืนยันว่ามีป๊อปอัปปรากฏขึ้น → ตรวจสอบ cluster / NAMESPACE / ชื่อโหลด → ยืนยันการรีสตาร์ท 

ป๊อปอัปยืนยันระบุอย่างชัดเจนว่า "การรีสตาร์ทจะทำให้ Pods ถูกสร้างใหม่ และบริการอาจถูกรบกวนสั้น ๆ" การรีสตาร์ทจะสร้าง Pods ใหม่บนทุกโหนดพร้อมกัน 

### 3.2 พ็อด
**ขั้นตอนการดำเนินงาน**: ไปที่พ็อดจากเมนูด้านซ้าย → ส่วนด้านล่างจะแสดงรายการพ็อดทั้งหมดภายใต้ NAMESPACEปัจจุบัน รองรับการค้นหาตาม Namespace, POD_NAME, IP ของพ็อด, และ NODE_IP 

สิ่งนี้ YAML ใช้สำหรับการดูเท่านั้น.

### 3.3 งานและ CronJobs

#### งาน
**ขั้นตอน**: ไปที่ งาน จากเมนูด้านซ้าย → ตารางจะแสดงรายการงานทั้งหมดในปัจจุบัน NAMESPACE.

สามารถค้นหาได้ตาม Namespaces และ Name

#### งาน Cron
**ขั้นตอน**: ไปที่ CronJobs จากเมนูด้านซ้าย → ตารางจะแสดงรายการ CronJobs ทั้งหมดภายใต้หน้า NAMESPACE.

สามารถค้นหาตาม Namespaces และ Name ได้ 
คลิก **** **** เพื่อขยายและแสดงตารางย่อยของ Pods ที่สอดคล้องกับ Jobs ทั้งหมดที่ถูกกระตุ้นโดย CronJob นี้ 

### 3.4 DaemonSets 
**ขั้นตอนการดำเนินงาน**: เข้าสู่ DaemonSets จากเมนูด้านซ้าย 

สามารถค้นหาตาม Namespaces และชื่อ workload ได้
การดำเนินการที่รองรับ:

- แก้ไข: CPU / Memory สามารถเปลี่ยนแปลงได้ แต่จำนวน replicas ไม่สามารถเปลี่ยนแปลงได้
- รีสตาร์ท: สร้าง Pods ใหม่บนโหนดทั้งหมดพร้อมกัน
- YAML: ดูอย่างเดียว

### 3.5 StatefulSets
**ขั้นตอนการดำเนินงาน**: ไปที่ StatefulSets จากเมนูด้านซ้าย → มุมมองตาราง

การแก้ไขจำนวน replicas CPU/หน่วยความจำ การรีสตาร์ท หรือรายการ Pod ของ StatefulSets ไม่ได้รับการสนับสนุน การเปลี่ยนแปลงที่จำเป็นควรทำโดยใช้ `kubectl` แบบเนทีฟ (ดูภาคผนวก B)

## 4. การกำหนดค่า

### 4.1 ConfigMaps
**ขั้นตอน**: เข้าสู่ ConfigMaps จากเมนูด้านซ้าย → ตารางจะแสดง ConfigMaps ทั้งหมดในปัจจุบัน NAMESPACE.
[การจัดการคลัสเตอร์] ไม่สนับสนุนการแก้ไขคีย์-ค่า สำหรับการเปลี่ยนแปลง กรุณาไปที่ศูนย์การกำหนดค่า

### 4.2 HPA
**ขั้นตอนการดำเนินงาน**: เข้าสู่ HPA จากเมนูด้านซ้าย → ตารางจะแสดง HPA ทั้งหมดภายใต้ปัจจุบัน NAMESPACE.

ดูได้เฉพาะ หากต้องการแก้ไข HPA ค่าต่ำสุดและสูงสุด กรุณาใช้แบบเนทีฟ `kubectl`.

## 6. การดำเนินงานทั่วไป

### 6.1 การแก้ไขปัญหา Pod

1. ใช้เมนูแบบเลื่อนด้านบนเพื่อสลับไปยังคลัสเตอร์ที่สอดคล้องและ NAMESPACE
2. ไปที่ Pods ในเมนูซ้าย
3. กรองโดย POD_NAME หรือ IP
4. ให้สังเกตฟิลด์ Phase ที่ด้านบนของการ์ด และให้ความสำคัญ `Failed` และ `Pending`
5. Condition ที่ตรงกับตัวชี้วัดสุขภาพสีเทาคือจุดที่มีปัญหา
6. คลิกไอคอน "Events" ที่ด้านท้ายของแถวเพื่อหาสาเหตุหลัก
7. ใช้ "Logs" เพื่อดูผลลัพธ์แบบเรียลไทม์ / "Crash Logs" เพื่อดูผลลัพธ์ของคอนเทนเนอร์ล่าสุด

### 6.2 รีสตาร์ท Deployment

1. ไปที่ Deployments ในเมนูซ้าย
2. ค้นหา Deployment เป้าหมาย
3. คลิกไอคอนลูกศรหมุนที่มุมขวาบน
4. ยืนยันป๊อปอัพโดยตรวจสอบคลัสเตอร์ / NAMESPACE / ชื่อ workload → ยืนยันการรีสตาร์ท
5. สังเกตแถบสถานะของ Pod replicas ที่ด้านล่างของการ์ดเพื่อประเมินความคืบหน้าการสร้างใหม่

### 6.3 ลดจำนวน Deployment Replicas เพื่อตรวจสอบ

1. เข้าไปที่ Deployment ที่เกี่ยวข้อง
2. คลิกไอคอนดินสอ "Edit"
3. ใส่ค่าจำนวน replicas ใหม่ (สามารถตั้งเป็น 0 เพื่อดีบัก) 
4. ปรับ CPU / Memory ตามที่จำเป็น (ไม่บังคับ) 
5. ยืนยันการเปลี่ยนแปลงและรอให้การอัปเดตแบบม้วนเกิดขึ้น 

ก่อนลดจำนวนสำเนา ควรแนะนำให้ยืนยันกับเพื่อนร่วมงานว่าค่าที่ตั้งไว้จะมีผลกระทบต่อการจราจรออนไลน์หรือไม่ SRE  

### 6.4 แก้ไข ConfigMap 

แพลตฟอร์มไม่รองรับการแก้ไขคู่ค่า key-value ของ ConfigMap ในการจัดการคลัสเตอร์ - การกำหนดค่า - ConfigMap โปรดไปที่ศูนย์กำหนดค่า

## 9. คำถามที่พบบ่อย 

**ถาม1: ภาพรวมด้านบนแสดงอัตราการทำงานของแอปพลิเคชันไม่ถึง 100%** 

นี่หมายความว่ามี Pods ภายใต้ปัจจุบัน NAMESPACE ที่ไม่อยู่ในสถานะ Ready (รวมถึง Pending, CrashLoopBackOff, Error ฯลฯ) โปรดไปที่เมนู Pods ทางด้านซ้าย กรองตาม POD_NAME หรือ IP และตรวจสอบเหตุการณ์และบันทึกของแต่ละ Pod ที่ไม่พร้อม 

**ถาม2: หน้าต่างป๊อปอัปว่างหลังจากคลิก 'แก้ไข Deployment'** 

มีสาเหตุสามประการที่พบบ่อย: การสัญญาณเครือข่ายไม่เสถียร, มี `managedFields` ในอ็อบเจ็กต์ทรัพยากรมากเกินไป หรือเซิร์ฟเวอร์ API เกิดข้อผิดพลาด โปรดปิดการลองใหม่ก่อน; หากยังว่างอยู่ ให้ติดต่อ SRE และระบุชื่อ cluster / namespace / workload สำหรับแก้ไขปัญหา 

**ถาม3: เนื้อหาป๊อปอัป YAML มีขนาดใหญ่มาก** 

เป็นปรากฏการณ์ปกติ K8s วัตถุ resource โดยค่าเริ่มต้นจะมี metadata และเงื่อนไขมากมาย โดยเนื้อหาสำคัญจะอยู่ใน `spec` ส่วน 

**คำถามที่ 4: ไม่มีผลลัพธ์ในหน้าต่างป็อปอัป log** 

คอนเทนเนอร์อาจจะไม่ได้ส่งออก log ไปยัง stdout/stderr กรุณาตรวจสอบนโยบายการส่งออก log ของแอปพลิเคชัน หากคอนเทนเนอร์ล้มเหลว ให้ใช้ไอคอน "Crash Log" เพื่อดึงผลลัพธ์จากอินสแตนซ์ก่อนหน้า 

**คำถามที่ 5: การแก้ไขจำนวน replica หรือ resource ไม่ได้มีผล** 

แพลตฟอร์มจะออก Strategic Merge Patch และ K8s จะเข้าสู่กระบวนการ reconcile ภายในไม่กี่วินาที หากไม่มีการเปลี่ยนแปลงภายใน 30 วินาที กรุณากลับไปที่ `kubectl describe deployment` เพื่อตรวจสอบ events 

**คำถามที่ 6: ไม่สามารถแก้ไข StatefulSets, ConfigMaps, HPA, Services, Ingresses** 

แพลตฟอร์มอนุญาตเฉพาะการดู resource เหล่านี้ การแก้ไขควรทำผ่านการตั้งค่า global ของ mdp และรองรับเฉพาะ Services และ Ingresses

## ภาคผนวก A: คำสั่งสำคัญ kubectl ที่ใช้ในแพลตฟอร์มนี้ 

คำสั่งต่อไปนี้ใช้เพื่อรันโดยตรงบน host หรือ maintenance terminal เป็นทางเลือกเมื่อฟังก์ชันของโมดูลนี้ไม่ได้ครอบคลุม 

```bash
# View
kubectl get  statefulset <name> -n <ns>
kubectl get deployment <name> -n <ns>

# Restart STS / deployment
kubectl rollout restart statefulset/<name> -n <ns>
kubectl rollout restart deployment/<name> -n <ns>

# View the complete Ingress rule chain
kubectl describe ingress <name> -n <ns>
```

`kubectl describe deployment <name> -n <ns>` สามารถใช้เพื่อแก้ไขปัญหาความคืบหน้าของการปรับปรุงที่ออกโดยแพลตฟอร์มหลังจากการแก้ไข

ข้อควรระวัง:
การแก้ไขทรัพยากรที่จัดการโดย MDP เช่น Deployment, ConfigMap, Ingress, StatefulSet, ฯลฯ ผ่าน kubectl ควรหลีกเลี่ยง วิธีการปฏิบัติที่ถูกต้องคือใช้การกำหนดค่า backend MDP
