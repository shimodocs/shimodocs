# การสำรองข้อมูล

[← ShimoDocs Suite เอกสารการติดตั้ง](../README.md)

เอกสารฉบับนี้อธิบายขอบเขตของการสำรองข้อมูล ข้อกำหนดการกู้คืน วิธีการดำเนินการ และรายการยืนยันหลังการกู้คืนสำหรับ ShimoDocs สภาพแวดล้อมที่เป็นส่วนตัว

เอกสารฉบับนี้ครอบคลุมเนื้อหาต่อไปนี้:

* ขอบเขตการสำรองข้อมูลและขอบเขตความรับผิดชอบ

* ข้อกำหนดการสำรองและกู้คืนฐานข้อมูล

* ข้อกำหนดการสำรองและกู้คืนการจัดเก็บวัตถุ

* รายการยืนยันก่อนการกู้คืน

* รายการยืนยันหลังการกู้คืน

เอกสารฉบับนี้ไม่ครอบคลุมเนื้อหาต่อไปนี้:

* ขั้นตอนการติดตั้งและปรับใช้งานครั้งแรก

* แผนการอัปเกรดและการย้ายข้อมูล

* คำแนะนำการใช้เครื่องมือกู้คืนเฉพาะของผู้ขายมิดเดิลแวร์ของบุคคลที่สาม

* กระบวนการจัดการเหตุการณ์ในระบบการผลิต

# 2. ขอบเขตการสำรองข้อมูลและขอบเขตความรับผิดชอบ

## 2.1 ขอบเขตการสำรองข้อมูล

ข้อมูลที่ต้องรวมอยู่ในขอบเขตการสำรองข้อมูลใน ShimoDocs สภาพแวดล้อมที่ถูกเอกชนประกอบด้วย:

* MySQL ข้อมูล

* MongoDB ข้อมูล

* Redis ข้อมูล

* ข้อมูลการจัดเก็บวัตถุ 

* ไฟล์การติดตั้ง การกำหนดค่า และพารามิเตอร์ของสภาพแวดล้อม 

ไดเรกทอรีข้อมูล ไดเรกทอรีสำรอง และระยะเวลาการเก็บสำรองจะถูกจัดการอย่างเป็นเอกภาพโดยฝั่งไคลเอนต์ 

## 2.2 ขอบเขตความรับผิดชอบ 

ขอบเขตของความรับผิดชอบในการสำรองและกู้คืนข้อมูลมีดังต่อไปนี้: 

* ฝั่งลูกค้ารับผิดชอบในการกำหนดนโยบายสำรองข้อมูลอย่างเป็นทางการและดำเนินการตามนั้น 

* ฝั่งลูกค้ารับผิดชอบในการเก็บรักษาไฟล์สำรองข้อมูล ความปลอดภัยของสื่อ และการจัดการระยะเวลาการเก็บรักษา 

* ฝั่งลูกค้ารับผิดชอบในการฝึกซ้อมการกู้คืน การอนุมัติการกู้คืน และการยอมรับผลลัพธ์การกู้คืน 

* ShimoDocs สามารถให้การสนับสนุนทางเทคนิคและคำแนะนำในการดำเนินการกู้คืน 

เมื่อมีการใช้ซอฟต์แวร์กลางภายนอก ระบบจัดเก็บข้อมูลแบบสร้างเอง หรือโครงสร้างพื้นฐานที่ดูแลโดยลูกค้า กลยุทธ์การสำรองและกู้คืนทั้งหมดจะดำเนินการโดยฝั่งลูกค้า 

# 3. การยืนยันก่อนการดำเนินการกู้คืน 

การกู้คืนข้อมูลเป็นการดำเนินการที่มีความเสี่ยงสูง การยืนยันดังต่อไปนี้ต้องเสร็จสิ้นก่อนการดำเนินการ 

## 3.1 การยืนยันเป้าหมาย 

ก่อนการกู้คืน ให้ชี้แจงข้อมูลต่อไปนี้: 

* สภาพแวดล้อมเป้าหมาย 

* คลัสเตอร์เป้าหมาย โหนด NAMESPACE 

* ขอบเขตของข้อมูลที่จะกู้คืน 

* จุดเวลาการกู้คืน 

* ช่วงเวลาการดำเนินการ 

## 3.2 การยืนยันความเสี่ยง

ยืนยันรายการต่อไปนี้ก่อนการกู้คืน:

* ว่าการกู้คืนนี้จะเขียนทับข้อมูลออนไลน์ปัจจุบันหรือไม่

* ว่าการกู้คืนนี้ต้องหยุดทำงานหรือไม่

* ว่าการสำรองข้อมูลล่าสุดถูกเพิ่มไปยังข้อมูลออนไลน์ปัจจุบันแล้วหรือไม่

* ว่าจุดย้อนกลับหลังจากการกู้คืนล้มเหลวได้ถูกชี้แจงหรือไม่

## 3.3 การยืนยันความถูกต้องของสำรองข้อมูล

ตรวจสอบสิ่งต่อไปนี้ก่อนการกู้คืน:

* ไฟล์สำรองข้อมูลสมบูรณ์และอ่านได้

* จุดเวลาสำรองข้อมูลตรงตามวัตถุประสงค์การกู้คืน

* ไดเรกทอรีสำรองข้อมูลถูกเมานท์อย่างถูกต้อง

* ไฟล์การกำหนดค่าทั้งหมดที่จำเป็นสำหรับการกู้คืนสมบูรณ์

* ไฟล์สำรองข้อมูลผ่านการตรวจสอบความสามารถในการกู้คืน

# 4. กลยุทธ์การสำรองข้อมูล

## 4.1 การสำรองฐานข้อมูล

เกณฑ์การสำรองฐานข้อมูลมีดังนี้:

|:----|:----|:----|:----|:----|
|การใช้ ShimoDocs ซอฟต์แวร์กลางที่รวมมาในตัว|ระบบสำรองข้อมูลตามตารางที่กำหนด|วันละครั้ง|7 วัน|ดำเนินการโดยงานตามตารางที่กำหนดภายในคลัสเตอร์|
|ใช้มิดเดิลแวร์ที่ลูกค้าดูแลเอง|การสำรองข้อมูลฝั่งลูกค้า|วันละครั้งหรือมากกว่า|7 วันหรือมากกว่า|ดำเนินการตามนโยบายฝั่งลูกค้า|



การสำรองฐานข้อมูลต้องครอบคลุมอย่างน้อย:

* MySQL

* MongoDB

* Redis

## 4.2 การสำรองข้อมูล Object Storage

เกณฑ์การสำรองข้อมูล Object Storage มีดังนี้:

|ประเภทข้อมูล|วิธีการดำเนินการ|ความถี่|ระยะเวลาการเก็บรักษา|คำอธิบาย|
|:----|:----|:----|:----|:----|
|ข้อมูลธุรกิจใน Object Storage|การสำรองข้อมูลเย็นหรือการทำซ้ำเพื่อกู้คืนภัยพิบัติ|ดำเนินการตามระดับธุรกิจ|ดำเนินการตามนโยบายลูกค้า|ครอบคลุมเอกสารแนบและไฟล์วัตถุ|
|ข้อมูลการกำหนดค่า Object Storage|การสำรองข้อมูลการกำหนดค่า|สำรองข้อมูลแบบซิงโครไนซ์หลังจากมีการเปลี่ยนแปลง|ดำเนินการตามนโยบายลูกค้า|ครอบคลุมพารามิเตอร์การเข้าถึงและข้อมูลการติดตั้ง|



สำเนาหลายชุดใน Object Storage เป็นส่วนหนึ่งของกลไกความซ้ำซ้อนของคลัสเตอร์และไม่เทียบเท่ากับการสำรองข้อมูล

## 4.3 การสำรองไฟล์การกำหนดค่า

การกำหนดค่าต่อไปนี้ถูกรวมอยู่ในขอบเขตการสำรองข้อมูล:

* พารามิเตอร์การติดตั้ง

* การกำหนดค่าโดเมนและโพรโทคอล

* ที่อยู่ของการพึ่งพาภายนอกและข้อมูลพอร์ต

* ข้อมูลการเข้าถึงที่เก็บวัตถุ 

* ไฟล์กำหนดค่าที่เกี่ยวข้องกับธุรกิจ 

# 5. การกู้คืนฐานข้อมูล 

ส่วนนี้ใช้กับการกู้คืนข้อมูลทั้งหมด MySQL, MongoDB, และ Redis. 

## 5.1 การเตรียมก่อนการกู้คืน 

ดำเนินการเตรียมการต่อไปนี้ก่อนทำการกู้คืนฐานข้อมูล: 

* เตรียมไดเรกทอรีการกู้คืนบนโหนดเป้าหมาย ตัวอย่างเช่น `/data/restore` 

* วางข้อมูลที่จะกู้คืนลงในไดเรกทอรีการกู้คืน 

* ตรวจสอบให้แน่ใจว่าการกำหนดค่า middleware ใน `global_config.json` ไฟล์ตรงกับสภาพแวดล้อมปัจจุบัน 

* ตรวจสอบโหนดการกู้คืน จุดกู้คืน หน้าต่างการดำเนินการ และข้อมูลการอนุมัติ 

## 5.2 ตรวจสอบงานสำรองข้อมูล 

ตรวจสอบงานสำรองข้อมูลฐานข้อมูลที่กำหนดเวลาไว้: 

```plain
kubectl get cronjob
```


บันทึกข้อมูลต่อไปนี้เพิ่มเติมด้วย:

* ชื่อ CronJob

* เวลาการดำเนินการล่าสุด

* ผลลัพธ์การดำเนินการล่าสุด

* ไดเรกทอรีเก็บไฟล์สำรอง

## 5.3 การกลับมาดำเนินการ

การกู้คืนฐานข้อมูลดำเนินการผ่านงานครั้งเดียว และสคริปต์การกู้คืนอยู่ในภาพสำรอง

ขั้นตอนการดำเนินการมีดังนี้:

1. เตรียมรายการงานกู้คืน `db-restore.yaml`

2. แก้ไข `spec.template.spec.nodeName` ไปที่โหนดที่ตั้งไดเรกทอรีกู้คืน

3. แก้ไข `hostPath.path` ไปที่ไดเรกทอรีที่มีการกู้คืนข้อมูล

4. ดำเนินการ `kubectl apply -f db-restore.yaml` คำสั่งเพื่อทำการกู้คืนข้อมูล

รายการงานตัวอย่างมีดังนี้:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  labels:
    job-name: db-restore
  name: db-restore
spec:
  template:
    metadata:
      labels:
        job-name: db-restore
      name: db-restore
    spec:
      containers:
      - command:
        - /bin/sh
        - -c
        - cd /data/pri-init/scripts/backup && sh restore_all.sh
        image: registryo.shimo.im/smbase/backup:co
        imagePullPolicy: Always
        name: db-restore
        volumeMounts:
        - name: db-config
          mountPath: /data/pri-init/scripts/global_config.json
          subPath: global_config.json
        - name: data
          mountPath: /backup
      dnsPolicy: ClusterFirst
      nodeName: master-1
      volumes:
      - name: db-config
        configMap:
          name: init-invoker
          items:
          - key: global_config.json
            path: global_config.json
      - name: data
        hostPath:
          path: /data/restore
      imagePullSecrets:
      - name: ee
      restartPolicy: Never
      schedulerName: default-scheduler
```


## 5.4 คำแนะนำการดำเนินการ

หลังจากทำงานการกู้คืนฐานข้อมูลแล้ว ข้อมูลต่อไปนี้จะถูกย้อนกลับ:

* MySQL

* MongoDB

* Redis

ในช่วงเวลาการกู้คืน ข้อมูลทางธุรกิจอาจถูกเขียนทับ จัดการปิดระบบทั้งหมดและตรวจสอบข้อมูลก่อนดำเนินการ

# 6. การกู้คืนที่เก็บวัตถุ

ส่วนนี้ใช้กับ MinIO และ S3การกู้คืนที่เก็บวัตถุที่เข้ากันได้

## 6.1 วิธีการสำรองข้อมูล

วิธีการสำรองข้อมูลที่ใช้กันทั่วไปสำหรับที่เก็บวัตถุมีดังนี้:

|วิธี|สถานการณ์ที่ใช้ได้|คำอธิบาย|
|:----|:----|:----|
|การซิงค์สำเนา Rsync|สภาพแวดล้อมแบบสแตนด์อโลน|เหมาะสำหรับการสำรองข้อมูลเย็นระดับไดเรกทอรี|
|สแน็ปชอตดิสก์|สภาพแวดล้อมแบบสแตนด์อโลน|เหมาะสำหรับการกู้คืนอย่างรวดเร็วบนแพลตฟอร์มจัดเก็บข้อมูลเดียวกัน|
|`mc mirror`|สภาพแวดล้อมแบบสแตนด์อโลนหรือแบบคลัสเตอร์|เหมาะสำหรับการสำรองข้อมูลเย็นและการกู้คืนข้อมูลวัตถุ|
|การจำลองสถานที่ / การจำลองบัคเก็ต|สภาพแวดล้อมแบบคลัสเตอร์|เหมาะสำหรับการทำสำเนากู้คืนจากภัยพิบัติ|



## 6.2 การกลับมาทำงาน

วิธีการกู้คืนที่ใช้ทั่วไปในสภาพแวดล้อมแบบสแตนด์อโลนมีดังนี้:

* เมื่อใช้ Rsync สำหรับสำรองข้อมูล ให้ทำการซิงโครไนซ์ย้อนกลับเพื่อกู้คืนไดเรกทอรีข้อมูล

```plain
rsync -av backup:/data/minio/ /data/minio/
```


* เมื่อใช้ `mc mirror` สำหรับสำรองข้อมูล ให้ทำการกู้คืนมิเรอร์ย้อนกลับ

```plain
mc mirror backup-minio/ new-minio/
```


แนวทางการกู้คืนสำหรับสภาพแวดล้อมแบบคลัสเตอร์มีดังนี้:

* เมื่อมีสำเนาการกู้คืนจากภัยพิบัติ ให้ทำการกู้คืนตามแผนการสลับระหว่างหลัก-สำรอง

* เมื่อใช้การสำรองข้อมูลแบบเย็น ให้ทำการกู้คืนตามไดเรกทอรีข้อมูลของการจัดเก็บวัตถุหรือเนื้อหาของที่เก็บรูปภาพ

## 6.3 คำสั่งการดำเนินการ

ก่อนการกู้คืนการจัดเก็บวัตถุ จำเป็นต้องยืนยันเรื่องดังต่อไปนี้:

* ช่วงถังเป้าหมายที่กู้คืน

* จุดกู้คืน

* ว่าจะเขียนทับวัตถุออนไลน์หรือไม่

* เส้นทางเก็บข้อมูลเป้าหมายและการกำหนดสิทธิ์

* ACCESS_DOMAIN และการกำหนดค่าเกตเวย์หลังการกู้คืน

# 7. การตรวจสอบหลังการกู้คืน

หลังการกู้คืนเสร็จสิ้น อย่างน้อยต้องตรวจสอบดังต่อไปนี้:

* สถานะบริการฐานข้อมูลเป็นปกติ

* สถานะบริการเก็บข้อมูลแบบออบเจ็กต์ปกติ

* สามารถจัดการผ่านแผงผู้ดูแลระบบได้

* การเข้าสู่ระบบของผู้ใช้ปกติ

* เอกสารหลักสามารถสร้าง แก้ไข บันทึก นำเข้า และส่งออกได้ตามปกติ

* จุดกู้คืนข้อมูลตรงตามความคาดหมาย

บันทึกข้อมูลต่อไปนี้หลังจากที่การกู้คืนเสร็จสมบูรณ์:

* เวลาที่ดำเนินการกู้คืน
