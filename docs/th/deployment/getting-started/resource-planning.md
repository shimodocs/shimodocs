# การวางแผนทรัพยากร

[← ShimoDocs Suite เอกสารการติดตั้ง](../README.md)

## 1. วัตถุประสงค์ของเอกสาร

เอกสารนี้ใช้เป็นแนวทางในการวางแผนทรัพยากรเซิร์ฟเวอร์และมิดเดิลแวร์ในสถานการณ์การปรับใช้งานในลักษณะส่วนบุคคล สำหรับอ้างอิงโดยวิศวกรที่ดำเนินการติดตั้ง วิศวกรปฏิบัติการ และบุคลากรสนับสนุนทางเทคนิคก่อนการขาย

เนื้อหาของเอกสารนี้อิงตามการวางแผนความจุของโครงการในอดีต การกำหนดค่าตัวอย่าง และมาตรฐานมิดเดิลแวร์ และสามารถใช้สำหรับการประมาณการก่อนการขาย การขอใช้ทรัพยากร การปรับใช้งาน และการประเมินการขยายตัวในอนาคต

## 2. ขอบเขตและคำแนะนำ

### 2.1 ขอบเขต

เอกสารนี้ใช้กับการวางแผนเบื้องต้นของโหนดแอปพลิเคชันและทรัพยากรมิดเดิลแวร์สำหรับผู้ใช้ที่มีขนาดต่างกันในสถานการณ์การปรับใช้งานในลักษณะส่วนบุคคล

### 2.2 คำแนะนำ

* การกำหนดค่าที่ระบุในเอกสารนี้เป็นการกำหนดค่าที่แนะนำทั้งหมด ใช้สำหรับการประเมินความสามารถของโครงการในระยะเริ่มต้นและการวางแผนทรัพยากร

* ทรัพยากรของโหนดแอปพลิเคชันและทรัพยากรของมิดเดิลแวร์ควรคำนวณแยกกัน ไม่แนะนำให้วางแผนผสม

* ในสถานการณ์ผู้ใช้ขนาดใหญ่ ทรัพยากรมิดเดิลแวร์จำเป็นต้องปรับเทียบเพิ่มเติมโดยพิจารณาจากภาระธุรกิจสูงสุด แบบจำลองความพร้อมกัน ผลการทดสอบความสามารถ และข้อมูลการติดตามการผลิต

* ในสภาพแวดล้อมการผลิตอย่างเป็นทางการ แนะนำให้สำรองความสามารถในการขยายและให้ความสำคัญกับการสร้างความพร้อมใช้งานสูง

* หากใช้เซิร์ฟเวอร์สถาปัตยกรรมภายในประเทศ CPU แนะนำให้ประมาณทรัพยากรรวมเป็นสองเท่าของสเปคมาตรฐาน

## 3. หลักการวางแผน

### 3.1 หลักการการปรับใช้แอปพลิเคชันและมิดเดิลแวร์

* สำหรับสถานการณ์ที่มีผู้ใช้น้อยกว่า 10,000 คน สามารถประเมินได้ว่าควรปรับใช้มิดเดิลแวร์บางส่วนภายใน K8s คลัสเตอร์ขึ้นอยู่กับสถานการณ์โครงการจริง

* สำหรับสถานการณ์ที่มีผู้ใช้งาน 10,000 คนขึ้นไป แนะนำให้ติดตั้งโหนดแอปพลิเคชันและมิดเดิลแวร์แยกกันอย่างสมบูรณ์

* มิดเดิลแวร์หลัก เช่น ฐานข้อมูล แคช คิวข้อความ และบริการค้นหา แนะนำให้ติดตั้งด้วยสถาปัตยกรรมความพร้อมสูงเป็นลำดับแรก

* เมื่อเงื่อนไขเอื้ออำนวย แนะนำให้ให้ความสำคัญกับการใช้บริการมิดเดิลแวร์แบบมีการจัดการบนคลาวด์สาธารณะที่มีความพร้อม เพื่อปรับปรุงความเสถียรและความสะดวกในการบำรุงรักษา

### 3.2 หลักการวางแผนการจัดเก็บวัตถุ

* ควรใช้บริการจัดเก็บวัตถุของคลาวด์สาธารณะ เช่น Alibaba Cloud OSS, Huawei Cloud OBS, Tencent Cloud COS, AWS S3.

* หากมีการติดตั้งระบบจัดเก็บวัตถุแบบส่วนตัว, SSD ต้องถูกใช้ และต้องประเมินประสิทธิภาพ ความเสถียร และความสามารถในการปฏิบัติงานหลังจากการเพิ่มความจุอย่างรอบคอบ

* หากธุรกิจเกี่ยวข้องกับการอัปโหลด ดาวน์โหลด พรีวิวไฟล์ขนาดใหญ่จำนวนมาก หรือสถานการณ์การแก้ไขสเปรดชีตขนาดใหญ่แบบร่วมกันหลายผู้ใช้ แนะนำให้ให้ความสำคัญกับการใช้บริการที่เก็บข้อมูลอ็อบเจ็กต์อิสระ

## 4. การวางแผนโหนดแอปพลิเคชัน

### 4.1 การจำแนกประเภทสเปคโหนดแอปพลิเคชัน

#### สเปค A

* สเปคที่แนะนำ: `24C / 48G / >=500G SSD * N`

* ช่วงการใช้งานที่เหมาะสม: ผู้ใช้น้อยกว่า 10,000 คน

* ฟีเจอร์ที่ใช้งานได้: 

   * สามารถรองรับสถานการณ์ธุรกิจขนาดเล็กถึงขนาดกลาง 

   * สามารถปรับใช้มิดเดิลแวร์ใน K8s สภาพแวดล้อมขึ้นอยู่กับโครงการ 

   * โหนดเดียวแบกรับภาระสูง; เมื่อโหนดล้มเหลว ผลกระทบค่อนข้างกว้าง 

#### สเปค B 

* สเปคที่แนะนำ: `16C / 32G / >=300G SSD * N` 

* ขอบเขตที่ใช้ได้: ผู้ใช้ 10,000 คนขึ้นไป 

* ฟีเจอร์ที่ใช้งานได้: 

   * เหมาะสำหรับการปรับใช้ขนาดใหญ่และมีความพร้อมใช้งานสูง 

   * ต้องใช้ซอฟต์แวร์กลางอิสระ 

   * ใช้วิธีหลายโหนดขนาดเล็ก ให้การจัดตารางที่สมดุลมากขึ้นและการปรับขนาดที่ยืดหยุ่นมากขึ้น 

   * เมื่อโหนดใดโหนดหนึ่งอยู่ระหว่างการบำรุงรักษาหรือมีปัญหา ผลกระทบต่อธุรกิจโดยรวมจะน้อยลง 






### 4.2 เกณฑ์การคำนวณโหนดแอปพลิเคชัน 

อิงจากตัวอย่างโครงการที่มีอยู่และกฎการคำนวณความจุ แนะนำให้ประมาณโหนดแอปพลิเคชันโดยใช้สูตรดังต่อไปนี้: 

`Number of nodes = Number of users × 0.03 ÷ 160` 

สามารถเข้าใจได้อย่างง่ายๆ ดังนี้: 

`Number of nodes ≈ Number of users ÷ 5300`

ที่ไหน:

* ค่าสัมประสิทธิ์ผู้ใช้งานพร้อมกันถูกประเมินที่ `0.03`.

* ความสามารถของโนดเดียว `16C / 32G` มีประมาณ `150 ~ 180 QPS`.

* แนะนำให้ใช้ `160 QPS/node` เป็นพื้นฐานในการคำนวณ

* ผลลัพธ์ที่คำนวณได้แนะนำให้ปัดขึ้น พร้อมสำรองความจุเพิ่มเติมเพื่อการขยายตัว

### 4.4 ข้อสรุปการวางแผนโหนดแอปพลิเคชัน

* ผู้ใช้ต่ำกว่า 10,000 คน แนะนำให้ใช้สเปค A

* ผู้ใช้ตั้งแต่ 10,000 คนขึ้นไป แนะนำให้ใช้สเปค B

* สำหรับขนาดผู้ใช้ 100,000 คน สามารถเริ่มต้นด้วย 18 หน่วยตามตัวอย่างหลักยึด และขนาดอื่นๆ ประมาณตามสูตรเดียวกันและปัดขึ้น

* สำหรับโครงการที่มีการเติบโตอย่างต่อเนื่อง แนะนำให้ดำเนินกลยุทธ์การขยายเป็นขั้นตอนเพื่อลดการลงทุนครั้งเดียวที่มากเกินไป

## 5. การวางแผนมิดเดิลแวร์

### 5.1 หลักการจำแนกประเภทมิดเดิลแวร์

การวางแผนทรัพยากรซอฟต์แวร์กลางปัจจุบันจะดำเนินการตามสองระดับมาตรฐานพื้นฐาน:

* `Users below 3,000`: ใช้การกำหนดค่ามาตรฐานขนาดเล็ก

* `3000 users and above`: ใช้การกำหนดค่ามาตรฐานขนาดใหญ่ 

สำหรับสถานการณ์ขนาดใหญ่ เช่น 10,000, 30,000, 50,000, 100,000, 200,000, 300,000, 500,000, 700,000 ผู้ใช้ แนะนำให้เริ่มต้นใช้การกำหนดค่ามาตรฐาน '3000 ผู้ใช้ขึ้นไป' อย่างสม่ำเสมอ และปรับขนาดตามการเติบโตของธุรกิจ

## 6. ข้อเสนอแนะเกี่ยวกับการนำไปใช้งานและการบำรุงรักษา

### 6.1 ข้อเสนอแนะการนำไปใช้งาน

* MySQL, MongoDB, Redis, Kafka, Elasticsearch แนะนำให้ติดตั้งในโหมดคลัสเตอร์ที่มีความพร้อมสูง

* หากสภาพแวดล้อมเอื้ออำนวย แนะนำให้ให้ความสำคัญกับการใช้บริการฐานข้อมูลและมิดเดิลแวร์ที่จัดการโดยคลาวด์สาธารณะเพื่อเพิ่มความเสถียรและความง่ายในการบำรุงรักษา

* สำหรับสถานการณ์ผู้ใช้ที่มี 10,000 คนขึ้นไป แนะนำให้แยกการติดตั้งโหนดแอปพลิเคชันและมิดเดิลแวร์ออกจากกัน 

* สำหรับ Kafkaแนะนำให้ใช้อินสแตนซ์แยกเพื่อหลีกเลี่ยงการใช้ทรัพยากรร่วมกับธุรกิจอื่น 

### 6.2 ข้อเสนอแนะการใช้ Object Storage 

* แนะนำให้ให้ความสำคัญกับการใช้ผลิตภัณฑ์ Object Storage บนคลาวด์สาธารณะ 

* หากใช้ Object Storage แบบส่วนตัว SSD จะต้องใช้ดิสก์ 

* หากพื้นที่ทีมเกี่ยวข้องกับสถานการณ์จำนวนมากในการอัปโหลด ดาวน์โหลด หรือพรีวิวไฟล์ขนาดใหญ่ ความจุ Object Storage, อัตราการส่งข้อมูล และแบนด์วิดท์ควรเป็นปัจจัยสำคัญในการประเมิน 

### 6.3 ข้อควรพิจารณาเรื่องการปรับขนาด 

ในสถานการณ์ธุรกิจต่อไปนี้ แนะนำให้ให้ความสำคัญกับการประเมินและเพิ่มทรัพยากรมิดเดิลแวร์: 

* การอัปโหลด ดาวน์โหลด หรือพรีวิวไฟล์แนบจำนวนมาก 

* การค้นหาข้อความเต็มบ่อยครั้ง 

* การสะสมข้อความหรือการทำงานแบบอะซิงโครนัสเข้มข้น 

* การเขียนเป็นชุดและการวิเคราะห์สถิติในช่วงที่มีผู้ใช้สูงสุด 

* ปริมาณล็อกที่เติบโตอย่างต่อเนื่อง 

เมตริกสำคัญที่ควรให้ความสนใจ ได้แก่: 

* ฐานข้อมูล: CPU, หน่วยความจำ, ดิสก์ IO 

* Redis: จำนวนการเชื่อมต่อ, อัตราการเข้าถึง, การใช้แบนด์วิดท์ 

* Kafka: จำนวนโบรกเกอร์, การสะสมข้อความ, พื้นที่ดิสก์ 

* Elasticsearch: จำนวนโหนด ขนาดดัชนี ความจุในการเก็บข้อมูล 

* การจัดเก็บวัตถุ: ประสิทธิภาพการอ่าน/เขียน ปริมาณคำขอ ความจุ แบนด์วิดท์ 






## 7. สรุป 

* สำหรับสถานการณ์ขนาดเล็ก (ผู้ใช้น้อยกว่า 10,000 คน) แนะนำให้ใช้การกำหนดค่าโหนดแอปพลิเคชันตาม Specification A และประเมินว่าควรติดตั้งซอฟต์แวร์เสริมบางส่วนภายในคลัสเตอร์หรือไม่ตามสถานการณ์ของโครงการ 

* สำหรับสถานการณ์ขนาดกลางและขนาดใหญ่ (ผู้ใช้ 10,000 คนขึ้นไป) แนะนำให้ใช้การกำหนดค่าโหนดแอปพลิเคชันตาม Specification B ควบคู่กับซอฟต์แวร์เสริมอิสระและสถาปัตยกรรมความพร้อมใช้งานสูง 
* แนะนำให้ทำการกำหนดค่าซอฟต์แวร์เสริมโดยอิงตามสองเกณฑ์: "ต่ำกว่า 3000 ผู้ใช้" และ "3000 ผู้ใช้ขึ้นไป" สำหรับโครงการขนาดใหญ่ การขยายตัวต่อเนื่องจะอิงตามการทดสอบความทนทานและข้อมูลการตรวจสอบ 
* ก่อนการดำเนินงานอย่างเป็นทางการ ควรยืนยันการวางแผนทรัพยากร ตรวจสอบความเข้ากันได้ และทดสอบความทนทานของความจุพร้อมกัน เพื่อหลีกเลี่ยงความแตกต่างระหว่างสเปกการติดตั้งและขอบเขตที่รองรับจริง 

* หากใช้ CPU เซิร์ฟเวอร์สถาปัตยกรรม แนะนำให้ประเมินทรัพยากรเป็นสองเท่าของสเปกมาตรฐาน 

* คู่มือนี้สำหรับการเลือกก่อนการติดตั้งและไม่สามารถแทนการทดสอบความทนทานในสถานที่หรือการดำเนินการสุดท้ายได้
