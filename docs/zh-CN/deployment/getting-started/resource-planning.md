# 资源规划

[← ShimoDocs Suite 部署文档](../README.md)

## 1. 文档目的

本文件用于指导私有化部署场景下服务器和中间件资源的规划，供实施工程师、运维工程师及售前技术支持人员参考。

文档内容基于历史项目容量规划、示例配置和中间件基线，可用于售前估算、资源申请、实施部署及后续扩展评估。

## 2. 范围和说明

### 2.1 范围

本文件适用于私有化部署场景下不同用户规模的应用节点和中间件资源的初步规划。

### 2.2 说明

* 本文件中的配置均为推荐配置，用于项目早期的容量评估和资源规划。

* 应用节点资源和中间件资源应分别计算，不建议混合规划。

* 在大规模用户场景下，中间件资源需要根据业务峰值、并发模型、容量压力测试结果及生产监控数据进行进一步校准。

* 在正式的生产环境中，建议预留扩展容量并优先进行高可用性建设。

* 如果使用国内的 CPU 架构服务器，建议将整体资源估算为标准规格的两倍。

## 3. 规划原则

### 3.1 应用和中间件部署原则

* 对于用户少于10,000的场景，可以评估是否在其中部署一些中间件 K8s 集群。

* 对于10,000名或更多用户的场景，建议将应用节点和中间件完全分开部署。

* 核心中间件如数据库、缓存、消息队列和搜索服务，建议优先部署高可用架构。

* 在条件允许的情况下，建议优先使用成熟的公共云托管中间件服务，以提高稳定性和可维护性。

### 3.2 对象存储规划原则

* 优先使用公共云对象存储服务，如阿里云 OSS、华为云 OBS、腾讯云 COS, AWS S3.

* 如果使用私有部署的对象存储， SSD 必须使用磁盘，并且在容量增长后需要仔细评估性能、稳定性和可操作性。

* 如果业务涉及大量大文件的上传、下载、预览或多用户协作的大型表格编辑场景，建议优先使用独立的对象存储服务。

## 4. 应用节点规划

### 4.1 应用节点规格分类

#### 规格 A

* 推荐规格： `24C / 48G / >=500G SSD * N`

* 适用范围：用户少于10,000人

* 适用功能： 

   * 可支持中小型企业场景 

   * 中间件可根据项目部署在 K8s 环境中 

   * 单节点承载高负载；当节点故障时，影响范围相对较大 

#### 规格 B 

* 推荐规格： `16C / 32G / >=300G SSD * N` 

* 适用范围：1万用户及以上 

* 适用功能： 

   * 适用于大规模、高可用部署场景 

   * 必须使用独立中间件 

   * 采用小规格多节点方式，提供更均衡的调度和更灵活的扩展 

   * 当某个节点进行维护或遇到问题时，对整体业务的影响较小 






### 4.2 应用节点计算标准 

基于现有项目示例及容量计算规则，建议应用节点按以下公式估算： 

`Number of nodes = Number of users × 0.03 ÷ 160` 

可以简单理解为： 

`Number of nodes ≈ Number of users ÷ 5300`

位置：

* 并发用户系数估计为 `0.03`.

* 单个节点的容量约为 `16C / 32G`  `150 ~ 180 QPS`.

* 建议使用 `160 QPS/node` 作为计算基础。

* 建议将计算结果进位，并为扩展预留额外容量。

### 4.4 应用节点规划结论

* 用户数量低于10,000建议使用规格A。

* 用户数量在10,000及以上建议使用规格B。

* 针对用户规模为100,000的情况，可按照样本锚点从18台开始，其他规模按统一公式估算并向上取整。

* 对于持续增长的项目，建议采用分阶段扩展策略，以避免一次性投资过高。

## 5. 中间件规划

### 5.1 中间件分类原则

当前中间件资源规划按两类基线执行：

* `Users below 3,000`：采用小规模基线配置。

* `3000 users and above`：采用大规模基线配置。 

对于更大规模场景，如10,000、30,000、50,000、100,000、200,000、300,000、500,000、700,000用户，建议统一从“3000用户及以上”基线配置开始，并根据业务增长动态扩展。

## 6. 实施及运维建议

### 6.1 部署实施建议

* MySQL, MongoDB, Redis, Kafka, Elasticsearch 建议以高可用集群模式部署。

* 条件允许时，建议优先使用公有云托管数据库及中间件服务，以提升稳定性和可维护性。

* 对于用户数量达到 10,000 或以上的场景，建议将应用节点与中间件分开部署。 

* 对于 Kafka，建议使用独立实例以避免与其他业务共享资源。 

### 6.2 对象存储实施建议 

* 建议优先使用公有云对象存储产品。 

* 如果使用私有对象存储， SSD 必须使用磁盘。 

* 如果团队空间涉及大量上传、下载或预览大文件的场景，对象存储的容量、吞吐量和带宽应作为主要评估因素。 

### 6.3 扩展考虑 

在以下业务场景中，建议优先评估并增加中间件资源： 

* 大量附件被上传、下载或预览 

* 高频率全文检索 

* 消息积累或密集的异步任务 

* 高峰期间的批量写入和统计分析 

* 日志量持续增长 

需要关注的关键指标包括： 

* 数据库： CPU、内存、磁盘 IO 

* Redis：连接数、命中率、带宽使用量 

* Kafka：代理数量、消息积累、磁盘空间 

* Elasticsearch：节点数量、索引大小、存储容量 

* 对象存储：读写性能、请求吞吐量、容量、带宽 






## 7. 结论 

* 对于小规模场景（用户少于 10,000），建议使用规范 A 的应用节点配置，并根据项目情况评估是否在集群内部署部分中间件。 

* 对于中大型场景（1万用户及以上），建议使用规格B应用节点配置，并配合独立中间件和高可用架构。 
* 中间件建议根据两个基线进行配置：“3000用户以下”和“3000用户及以上”。对于大型项目，持续扩展应基于压力测试和监控数据进行。 
* 在正式实施前，应同时完成资源规划确认、兼容性验证和容量压力测试，以避免部署规格与实际支持范围之间的不一致。 

* 如果使用国产 CPU 架构服务器，建议按标准规格的两倍估算资源。 

* 本手册用于安装前的选择参考，并不能替代现场压力测试或最终实施。
