# 데이터 백업

[← ShimoDocs Suite 배포 문서](../README.md)

이 문서는 프라이버시화된 환경에 대한 데이터 백업 범위, 복구 요구 사항, 실행 방법 및 복구 후 검증 항목을 설명합니다. ShimoDocs 

이 문서는 다음 내용을 다룹니다:

* 백업 범위 및 책임 경계

* 데이터베이스 백업 및 복구 요구 사항

* 객체 저장소 백업 및 복구 요구 사항

* 복구 전 확인 항목

* 복구 후 검증 항목

이 문서는 다음 내용을 포함하지 않습니다:

* 초기 설치 및 배포 단계

* 업그레이드 및 마이그레이션 계획

* 타사 미들웨어 벤더별 복구 도구 지침

* 운영 사고 처리 프로세스

# 2. 백업 범위 및 책임 경계

## 2.1 백업 범위

백업 범위에 포함해야 하는 데이터는 ShimoDocs 사유화된 환경에는 다음이 포함됩니다:

* MySQL 데이터

* MongoDB 데이터

* Redis 데이터

* 오브젝트 스토리지 데이터 

* 설치 구성 및 환경 매개변수 파일 

데이터 디렉토리, 백업 디렉토리 및 백업 보존 기간은 클라이언트 측에서 일괄 관리합니다. 

## 2.2 책임 범위 

백업 및 복구 책임의 범위는 다음과 같습니다: 

* 클라이언트 측은 공식 백업 정책을 수립하고 실행할 책임이 있습니다 

* 클라이언트 측은 백업 파일의 안전한 보관, 매체 보안 및 보존 기간 관리에 책임이 있습니다 

* 클라이언트 측은 복구 훈련, 복구 승인 및 복구 결과 수용에 책임이 있습니다 

* ShimoDocs 기술 지원 및 복구 운영 지침을 제공할 수 있습니다 

외부 미들웨어, 자체 구축 오브젝트 스토리지 또는 클라이언트가 유지 관리하는 인프라가 관련된 경우, 백업 및 복구 전략은 전적으로 클라이언트 측에서 수행됩니다. 

# 3. 복구 실행 전 확인 

데이터 복구는 고위험 작업입니다. 실행 전에 다음 확인이 완료되어야 합니다. 

## 3.1 대상 확인 

복구 전에 다음 정보를 명확히 하십시오: 

* 대상 환경 

* 대상 클러스터, 노드 NAMESPACE 

* 복구할 데이터 범위 

* 복구 시점 

* 실행 시간 

## 3.2 위험 확인

복구 전에 다음 항목을 확인하십시오:

* 이번 복구가 현재 온라인 데이터를 덮어쓸 것인지 여부

* 이번 복구가 다운타임을 필요로 하는지 여부

* 최신 백업이 현재 온라인 데이터에 추가되었는지 여부

* 복구 실패 후 롤백 지점이 명확히 설정되었는지 여부

## 3.3 백업 유효성 확인

복구 전에 다음 항목을 확인하십시오:

* 백업 파일이 완전하고 읽기 가능한지

* 백업 시점이 복구 목표를 충족하는지

* 백업 디렉터리가 올바르게 마운트되었는지

* 복구에 필요한 모든 구성 파일이 완전한지

* 백업 파일이 복구 가능성 검증을 통과했는지

# 4. 백업 전략

## 4.1 데이터베이스 백업

데이터베이스 백업 기준은 다음과 같습니다:

|시나리오|실행 방법|빈도|보존 기간|설명|
|:----|:----|:----|:----|:----|
|사용 ShimoDocs 내장 미들웨어|시스템 예약 백업|하루에 한 번|7일|클러스터 내 예약 작업에 의해 실행됨|
|고객이 직접 관리하는 미들웨어 사용|고객 측 백업|하루에 한 번 이상|7일 이상|고객 측 정책에 따라 실행|



데이터베이스 백업은 최소한 다음을 포함해야 함:

* MySQL

* MongoDB

* Redis

## 4.2 객체 저장소 백업

객체 저장소 백업 기준은 다음과 같음:

|데이터 유형|실행 방법|빈도|보존 기간|설명|
|:----|:----|:----|:----|:----|
|객체 저장소 업무 데이터|콜드 백업 또는 재해 복구 복제|업무 수준에 따라 실행|고객 정책에 따라 실행|문서 첨부 파일 및 파일 객체 포함|
|객체 저장소 구성 데이터|구성 백업|변경 후 동기화 백업|고객 정책에 따라 실행|접근 매개변수 및 마운트 정보 포함|



객체 저장소의 복제본 다수는 클러스터의 중복 메커니즘의 일부이며 데이터 백업과 동일하지 않음.

## 4.3 구성 파일 백업

다음 구성이 백업 범위에 포함됨:

* 설치 매개변수

* 도메인 및 프로토콜 구성

* 외부 종속 주소 및 포트 정보

* 객체 저장소 접근 정보 

* 비즈니스 관련 구성 파일 

# 5. 데이터베이스 복구 

이 섹션은 모든 데이터 복구에 적용됩니다 MySQL, MongoDB, 및 Redis. 

## 5.1 복구 전 준비 

데이터베이스 복구를 수행하기 전에 다음 준비를 완료하십시오: 

* 대상 노드에 복구 디렉토리를 준비하십시오, 예를 들어, `/data/restore` 

* 복구할 데이터를 복구 디렉토리에 배치하십시오 

* 파일의 미들웨어 구성이 현재 환경과 일치하는지 확인하십시오 `global_config.json`  

* 복구 노드, 복구 지점, 실행 창 및 승인 정보를 확인하십시오 

## 5.2 백업 작업 확인 

예약된 데이터베이스 백업 작업을 확인하십시오: 

```plain
kubectl get cronjob
```


다음 정보를 기록하십시오:

* CronJob 이름

* 마지막 실행 시간

* 최근 실행 결과

* 백업 파일 저장 디렉터리

## 5.3 실행 재개

데이터베이스 복구는 일회성 작업을 통해 수행되며, 복구 스크립트는 백업 이미지에 있습니다.

실행 단계는 다음과 같습니다:

1. 복원 작업 목록을 준비합니다 `db-restore.yaml`

2. 수정 `spec.template.spec.nodeName` 복구 디렉토리가 있는 노드로 이동

3. 수정 `hostPath.path` 데이터가 복원될 디렉토리로 이동

4. 다음을 실행 `kubectl apply -f db-restore.yaml` 데이터 복원을 수행하는 명령

샘플 작업 리스트는 다음과 같습니다:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  labels:
    job-name: db-restore
  name: db-restore
spec:
  template:
    metadata:
      labels:
        job-name: db-restore
      name: db-restore
    spec:
      containers:
      - command:
        - /bin/sh
        - -c
        - cd /data/pri-init/scripts/backup && sh restore_all.sh
        image: registryo.shimo.im/smbase/backup:co
        imagePullPolicy: Always
        name: db-restore
        volumeMounts:
        - name: db-config
          mountPath: /data/pri-init/scripts/global_config.json
          subPath: global_config.json
        - name: data
          mountPath: /backup
      dnsPolicy: ClusterFirst
      nodeName: master-1
      volumes:
      - name: db-config
        configMap:
          name: init-invoker
          items:
          - key: global_config.json
            path: global_config.json
      - name: data
        hostPath:
          path: /data/restore
      imagePullSecrets:
      - name: ee
      restartPolicy: Never
      schedulerName: default-scheduler
```


## 5.4 실행 지침

데이터베이스 복구 작업이 실행된 후, 다음 데이터가 롤백됩니다:

* MySQL

* MongoDB

* Redis

복구 기간 동안 비즈니스 데이터가 덮어쓰기될 수 있습니다. 실행 전에 완전 종료와 데이터 검증을 완료하십시오.

# 6. 객체 스토리지 복구

이 섹션은 다음에 적용됩니다 MinIO 그리고 S3-호환 객체 스토리지 복구.

## 6.1 백업 방법

객체 스토지의 일반적인 백업 방법은 다음과 같습니다:

|방법|적용 시나리오|설명|
|:----|:----|:----|
|Rsync 동기화 복사|단독 환경|디렉토리 수준의 콜드 백업에 적합|
|디스크 스냅샷|단독 환경|같은 스토리지 플랫폼에서 빠른 복구에 적합|
|`mc mirror`|단독 또는 클러스터 환경|객체 데이터 콜드 백업 및 복구에 적합|
|사이트 복제 / 버킷 복제|클러스터 환경|재해 복구 복제에 적합|



## 6.2 실행 재개

독립 실행 환경에서 일반적으로 사용되는 복구 방법은 다음과 같습니다:

* 백업에 Rsync를 사용하는 경우, 데이터 디렉터리를 복원하기 위해 역동기화를 수행

```plain
rsync -av backup:/data/minio/ /data/minio/
```


* 백업에 `mc mirror` 를 사용하는 경우, 역 방Mirror 복원을 수행

```plain
mc mirror backup-minio/ new-minio/
```


클러스터 환경에 대한 복구 지침은 다음과 같습니다:

* 재해 복구 사본이 존재하면, 주-대기 전환 계획에 따라 복구 수행

* 콜드 백업을 사용하는 경우, 객체 스토리지 데이터 디렉터리 또는 이미지 저장소의 내용에 따라 복구 수행

## 6.3 실행 지침

객체 스토리지를 복원하기 전에 다음 사항을 확인해야 합니다:

* 복원 대상 버킷 범위

* 복구 시점

* 온라인 객체 덮어쓰기 여부

* 대상 저장 경로 및 권한 설정

* ACCESS_DOMAIN 복구 후 게이트웨이 설정

# 7. 복구 후 검증

복구가 완료된 후 최소한 다음 사항을 검증합니다:

* 데이터베이스 서비스 상태가 정상임

* 객체 저장소 서비스 상태는 정상입니다

* 관리자 패널을 통해 관리 가능합니다

* 사용자 로그인은 정상입니다

* 핵심 문서는 정상적으로 생성, 편집, 저장, 가져오기 및 내보내기가 가능합니다

* 데이터 복구 시점은 기대치와 일치합니다

복구 완료 후 다음 정보를 기록합니다:

* 복구 실행 시간

* 데이터 복구 시점

* 실행자, 승인자, 검사자

* 복구 후 발견된 문제
