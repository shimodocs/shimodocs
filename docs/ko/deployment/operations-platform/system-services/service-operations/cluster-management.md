# 클러스터 관리

[← ShimoDocs Suite 배포 문서](../../../README.md)

## 1. 기능 개요

클러스터 관리 모듈은 콘솔입니다. MDP 고객과 인터페이스하는 운영 플랫폼 Kubernetes 클러스터로, 세 가지 시나리오를 대상으로 합니다: 일일 점검, 긴급 문제 해결, 자원 변경. 이 모듈의 목표는 근무 중인 운영 인력이 자주 네이티브로 전환하지 않고도 일반적인 문제 해결 및 운영 작업을 완료할 수 있도록 하는 것입니다. `kubectl`.

주요 기능:

- 클러스터 개요: 노드 상태, 애플리케이션 실행 상태
- 워크로드 관리: 보기, 재시작, 복제본 수 변경, 컨테이너 리소스 수정 및 보기 YAML Deployment, StatefulSet, DaemonSet, Pod, Job 및 CronJob
- 구성 관리: ConfigMap, HorizontalPodAutoscaler 보기HPA)
- 네트워크 리소스: Service, Ingress 보기
- Pod 수준 진단: 실시간 로그, 충돌 로그 K8s 이벤트, 웹 터미널, YAML 보기

### 1.1 적용 대상 사용자

| 역할        | 일반 작업                                      |
| ----------- | ---------------------------------------------------- |
| 당직 운영 | 노드 및 파드 이상 보기, 로그 조회, 이벤트 확인 |
| 현장 지원 | 배포 복제 상태, 이미지 버전, 리소스 요청/제한 보기         |
| 장애 긴급 대응 | 배포 또는 데몬셋 재시작, 복제 수 조정, 조정 CPU/메모리 |
| 용량 계획 | 보기 HPA 현재 복제 수 및 상한/하한 확인                             |

### 1.2 이 모듈에서 권장되지 않는 작업

삭제 NAMESPACE, 파드를 강제로 추방, 시크릿 또는 RBAC 리소스 수정 등 민감한 작업은 이 모듈에서 사용할 수 없으며, 네이티브 `kubectl` 또는 관련 변경 도구를 통해 실행해야 합니다. 크로스 클러스터 배치 작업은 불가하며, 각 작업은 선택된 클러스터에만 영향을 미칩니다. NAMESPACE대용량 로그 파일을 한 번에 다운로드할 경우 스트리밍 로그 팝업보다는 웹 터미널 사용을 권장합니다.

## 2. 진입 및 탐색

왼쪽 메뉴: **운영 관리 → 클러스터 관리**.

진입 후, **배포** 메뉴가 기본적으로 선택되어 있습니다. NAMESPACE 현재 클러스터에서 첫 번째 항목이 기본값이며, 클러스터와 NAMESPACE 의 사용자 지정 선택이 지원됩니다.

## 3. 워크로드

### 3.1 배포
**단계**: 대상 배포 찾기 → 오른쪽 상단의 연필 아이콘 클릭 → 편집 팝업 나타남 → 새 값 입력 → 변경 사항 확인.

팝업에서 수정 가능한 필드: 

- 복제본 수, 최소 값 0, 정수여야 함 
- CPU 컨테이너당 요청 / 제한, 단위는 '코어', 입력 가능 `1` 또는 `1000m` 
- 컨테이너당 메모리 요청 / 제한, 단위는 Mi, 입력 가능 `512` 

제출 후 롤링 재빌드가 트리거됩니다. 나열되지 않은 필드(이미지, 환경, 프로브 등)는 변경되지 않습니다. 

#### 3.1.1 배포 재시작 
단계: 대상 Deployment 찾기 → 오른쪽 상단의 원형 화살표 아이콘 클릭 → 팝업이 나타나는지 확인 → 클러스터 / NAMESPACE 로드 이름 확인 → 재시작 확인. 

확인 팝업에 "재시작하면 Pods가 재빌드되며 서비스가 잠시 중단될 수 있습니다."라고 명확히 표시됩니다. 재시작하면 모든 노드에서 Pods가 동시에 재빌드됩니다. 

### 3.2 포드
**작업 단계**: 왼쪽 메뉴에서 포드로 이동 → 하단 섹션에 현재의 모든 포드가 나열됩니다 NAMESPACE, 네임스페이스, POD_NAME, 포드 IP로 검색 지원 NODE_IP. 

이 YAML 는 보기 전용입니다.

### 3.3 잡 및 크론잡

#### 잡
**단계**: 왼쪽 메뉴에서 잡으로 이동 → 테이블에 현재의 모든 잡이 나열됩니다 NAMESPACE.

네임스페이스와 이름으로 검색 가능.

#### 크론잡
**단계**: 왼쪽 메뉴에서 크론잡으로 이동 → 테이블에 현재의 모든 크론잡이 나열됩니다 NAMESPACE.

네임스페이스와 이름으로 검색 가능. 
클릭 **** **** 이 크론잡에 의해 트리거된 모든 잡에 해당하는 포드의 하위 테이블을 확장하여 표시합니다. 

### 3.4 데몬셋 
**작업 단계**: 왼쪽 메뉴에서 데몬셋으로 들어갑니다. 

네임스페이스와 워크로드 이름으로 검색 가능.
지원되는 작업:

- 수정: CPU / 메모리는 변경 가능, 복제 수는 변경 불가.
- 재시작: 모든 노드에서 포드를 동시에 재구성.
- YAML: 보기 전용.

### 3.5 스테이트풀셋
**작업 단계**: 왼쪽 메뉴에서 스테이트풀셋으로 이동 → 테이블 보기.

복제 수 수정, CPU/메모리, 재시작 또는 StatefulSets의 Pod 목록은 지원되지 않습니다. 필요한 변경 사항은 네이티브 `kubectl` 을 사용하여 수행해야 합니다(부록 B 참조).

### 4.2 HPA
**작업 단계**: 입력 HPA 왼쪽 메뉴 → 현재 아래의 모든 HPA가 표에 나열됩니다 NAMESPACE.

보기 전용입니다. 수정하려면 HPA 최소값과 최대값을 변경하려면, 기본 기능을 사용하세요 `kubectl`.

## 6. 공통 작업

### 6.1 파드 문제 해결

1. 상단 드롭다운을 사용하여 해당 클러스터로 전환합니다. NAMESPACE
2. 왼쪽 메뉴에서 Pods로 이동
3. 필터 기준 POD_NAME 또는 IP
4. 카드 상단의 Phase 필드에 주의하고, 우선순위를 정하세요 `Failed` 그리고 `Pending`
5. 회색으로 표시된 상태 표시기에 해당하는 Condition이 문제 지점입니다
6. 행 끝의 "Events" 아이콘을 클릭하여 원인을 찾으세요
7. "Logs"를 사용하여 실시간 출력 확인 / "Crash Logs"를 사용하여 마지막 컨테이너 출력 확인

### 6.2 Deployment 재시작

1. 왼쪽 메뉴에서 Deployments로 이동
2. 대상 Deployment 찾기
3. 오른쪽 상단의 원형 화살표 아이콘을 클릭합니다
4. 팝업에서 클러스터 / 를 확인하여 확인합니다 NAMESPACE / 워크로드 이름 → 재시작 확인
5. 카드 하단의 Pod 레플리카 상태 진행 표시줄을 관찰하여 재구축 진행 상황을 판단합니다

### 6.3 검증을 위한 배포 레플리카 수 줄이기

1. 해당 Deployment에 들어갑니다
2. 연필 모양의 "편집" 아이콘을 클릭합니다
3. 레플리카 수의 새 값을 입력합니다 (디버깅을 위해 0으로 설정 가능) 
4. 조정 CPU / 필요에 따라 메모리 조정 (선택 사항) 
5. 변경 사항을 확인하고 롤링 업데이트가 완료될 때까지 기다립니다 

복제본 수를 줄이기 전에, 대상 값이 온라인 트래픽에 영향을 미치는지 동료와 확인하는 것이 좋습니다. SRE  

### 6.4 ConfigMap 수정 

플랫폼은 클러스터 관리 - 구성 - ConfigMap에서 ConfigMap 키-값 쌍 편집을 지원하지 않습니다. 구성 센터로 이동하십시오.

## 9. 자주 묻는 질문 

**Q1: 상단 개요에서 애플리케이션 실행률이 100%가 아닙니다.** 

이는 현재 NAMESPACE 상태가 Ready가 아닌 Pod(대기, CrashLoopBackOff, 오류 등 포함)가 있음을 의미합니다. 왼쪽의 Pods 메뉴로 이동하여 필터링하십시오. POD_NAME 또는 IP를 확인하고 각 Ready 상태가 아닌 Pod의 이벤트와 로그를 확인합니다. 

**Q2: '배포 수정'을 클릭한 후 팝업이 비어 있습니다.** 

세 가지 일반적인 이유가 있습니다: 네트워크 지터, 리소스 객체의 과다, 또는 서버 `managedFields` 예외. 먼저 재시도를 비활성화하세요; 여전히 비어 있다면, 연락하여 API 클러스터 / 네임스페이스 / 워크로드 이름을 제공하여 문제를 해결하십시오. SRE  

**Q3: YAML 팝업 내용이 매우 큽니다.** 

정상 현상. K8s 리소스 객체는 기본적으로 많은 메타데이터와 조건을 가지고 있으며, 주요 내용은 `spec` 섹션에 집중되어 있습니다. 

**Q4: 로그 팝업에 출력이 없습니다.** 

컨테이너가 stdout/stderr에 로그를 출력하지 않을 수 있으므로, 애플리케이션 로그 출력 정책을 확인하세요. 컨테이너가 충돌한 경우 "Crash Log" 아이콘을 사용하여 이전 인스턴스의 출력을 가져오세요. 

**Q5: 복제본 수 또는 리소스 수정이 적용되지 않았습니다.** 

플랫폼은 전략적 병합 패치를 발행하며, K8s 몇 초 내에 조정(reconcile) 프로세스가 시작됩니다. 30초 내에 변경 사항이 없으면, 원래 `kubectl describe deployment` 로 돌아가 이벤트를 확인하세요. 

**Q6: StatefulSets, ConfigMaps, HPA, Services, Ingresses를 수정할 수 없습니다.** 

플랫폼은 이러한 리소스의 보기만 허용합니다. 수정은 mdp 글로벌 설정을 통해 이루어져야 하며, Services와 Ingresses만 지원됩니다.

## 부록 A: 주요 kubectl 이 플랫폼에서 사용되는 명령어 

다음 명령어들은 이 모듈의 기능이 다루어지지 않을 경우, 호스트 또는 유지보수 터미널에서 직접 실행하는 대체 경로로 사용됩니다. 

```bash
# View
kubectl get  statefulset <name> -n <ns>
kubectl get deployment <name> -n <ns>

# Restart STS / deployment
kubectl rollout restart statefulset/<name> -n <ns>
kubectl rollout restart deployment/<name> -n <ns>

# View the complete Ingress rule chain
kubectl describe ingress <name> -n <ns>
```

`kubectl describe deployment <name> -n <ns>` 플랫폼에서 수정 후 발행된 조정(reconcile)의 진행 상황을 문제 해결하는 데 사용할 수 있습니다.

주의사항:
다음과 같은 관리되는 리소스를 수정하는 것은 MDP 배포(deployment), ConfigMap, Ingress, StatefulSet(STS) 등과 같이 kubectl 피해야 합니다. 올바른 운영 방법은 MDP 백엔드 구성을 사용하는 것입니다.
