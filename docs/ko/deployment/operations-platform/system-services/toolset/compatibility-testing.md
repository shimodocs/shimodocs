# 호환성 테스트

[← ShimoDocs Suite 배포 문서](../../../README.md)

## 1. 페이지 개요

호환성 테스트 페이지는 객체 스토리지 구성, 연결 상태, 업로드 호환성 및 업로드 성능을 확인하는 데 사용됩니다. 페이지는 다음과 같이 나뉩니다:

1. 스토리지 구성;
2. 호환성 테스트;
3. 성능 테스트.

## 2. 스토리지 구성 

### 2.1 구성 항목 설명 

| 구성 항목 | 기능 |
| --- | --- |
| 액세스 키 | 객체 스토리지 접근 아이덴티티 식별자, 즉 AK |
| 비밀 키 | AK와 함께 제공되는 접근 키, 즉 SK |
| 엔드포인트 | 객체 스토리지 서비스 주소 |
| 버킷 이름 | 감지할 대상 버킷 |
| 지역 | 스토리지 버킷 위치 영역 |
| 공용 엔드포인트 | 브라우저가 객체 스토리지에 접근할 때 사용하는 공용 도메인, 선택 사항 |
| 경로 스타일 | 'endpoint/bucket/object' 형식을 사용하여 객체에 접근, 일반적으로 서비스에서 활성화 필요 MinIO 필요 |

### 2.2 구성 입력 
1. 필요에 따라 '첨부 버킷 채우기' 또는 '콘텐츠 버킷 채우기' 클릭 
2. 시스템이 현재 환경에 해당하는 AK, SK, Endpoint, Bucket, Region 등의 구성을 자동으로 채움 
3. 자동 채우기를 사용하지 않는 경우 모든 구성을 수동으로 입력할 수도 있음 
4. 엔드포인트에 올바른 프로토콜과 포트가 포함되어 있는지 확인 
5. 버킷 이름이 이번에 감지할 버킷인지 확인 
6. Region이 객체 스토리지의 실제 지역과 일치하는지 확인
7. 브라우저가 객체 스토리지에 직접 접근해야 하는 경우, 공용 엔드포인트 입력
8. 객체 스토리지 유형에 따라 Path Style 사용 여부를 결정합니다.

이번에 Attachments 버킷을 자동으로 채운 후:

- 버킷: `shimo-attachments`;
- 엔드포인트: 시스템에서 자동으로 채움;
- 리전: `cn-north-1`;
- 공용 엔드포인트: 시스템에서 자동으로 채움;
- Path Style: 사용함.

"Contents 버킷 채우기"를 클릭하면 버킷이 자동으로 전환될 수 있습니다. `file-contents`.

> Secret Key는 민감한 정보입니다; 스크린샷, 채팅 또는 티켓에 평문으로 표시하지 마십시오.

## 3. 호환성 테스트

호환성 테스트는 백엔드 업로드, 브라우저 직접 업로드, 멀티파트 업로드 순으로 확인합니다.

### 3.1 테스트 시작

1. 스토리지 구성을 완료합니다.
2. "호환성 테스트" 탭을 클릭합니다.
3. 버킷, 엔드포인트, 리전, 공용 엔드포인트, Path Style 구성이 올바른지 다시 확인합니다.
4. "호환성 테스트 시작"을 클릭합니다.
5. 페이지에 "호환성 테스트 완료"라고 표시될 때까지 기다립니다.
6. 페이지의 요약 상태가 "모두 통과"인지 확인합니다.
7. 세 가지 테스트의 상태, 지속 시간 및 결과 정보를 각각 확인하십시오.

### 3.2 백엔드 업로드 테스트

이 테스트는 백엔드 서비스에서 객체 스토리지로의 네트워크 연결 및 쓰기 권한을 확인하는 데 사용됩니다.

1. 백엔드가 테스트 텍스트 파일을 생성합니다.
2. 백엔드가 파일을 대상 버킷에 씁니다.
3. 페이지에 업로드 지속 시간과 테스트 객체의 경로가 표시됩니다.
4. 녹색 성공 상태는 백엔드 네트워크와 쓰기 권한이 정상임을 나타냅니다.

현재 결과: 업로드 성공, 소요 시간 `157 ms`.

### 3.3 브라우저 직접 업로드 테스트

이 테스트는 브라우저가 PostPolicy를 통해 객체 스토리지로 직접 업로드할 수 있는 링크를 확인하는 데 사용됩니다.

1. 페이지가 직접 업로드에 필요한 PostPolicy를 백엔드로부터 요청합니다.
2. 브라우저가 퍼블릭 엔드포인트를 사용하여 파일을 객체 스토리지에 직접 업로드합니다.
3. 페이지가 다음을 확인합니다 HTTP 객체 스토리지에서 반환된 상태 코드를 확인합니다.
4. HTTP 204는 브라우저 직접 업로드가 성공했음을 나타냅니다.

이번 결과: 브라우저 직접 업로드 성공, 소요 시간 `61 ms`, 상태 코드 `204`.

### 3.4 다중 파트 업로드 테스트

이 테스트는 대용량 파일 다중 파트 업로드의 전체 과정을 검증하는 데 사용됩니다.

1. 다중 파트 업로드 작업을 초기화합니다.
2. 테스트 파일을 여러 부분으로 분할합니다.
3. 각 부분을 순차적으로 업로드합니다.
4. 객체 생성을 완료하기 위해 병합 인터페이스를 호출합니다.
5. 페이지에 다음이 표시됩니다 `multipart upload succeeded`, 전체 과정이 성공했음을 나타냅니다.

이번 결과: 다중 파트 업로드 성공, 소요 시간 `1746 ms`.

### 3.5 테스트 객체 설명

호환성 테스트는 실제로 대상 버킷에 쓰기를 수행하며, 백엔드 테스트 객체의 경로는 일반적으로 다음과 유사합니다:

```text
compatibility-tests/<RANDOM UUID>.txt
```

1. 테스트를 실행하기 전에 대상 버킷이 올바른지 확인하십시오.
2. 잘못된 운영 버킷에서 무분별하게 테스트를 실행하지 마십시오.
3. 테스트 후에는 환경의 정리 정책에 따라 테스트 객체를 확인하고 정리할 수 있습니다.

## 4. 성능 테스트

성능 테스트는 파일 크기에 따른 업로드 시간과 처리량을 측정하는 데 사용됩니다.

### 4.1 성능 테스트 구성

1. "성능 테스트" 탭을 클릭합니다.
2. 테스트 모드를 선택하세요; 페이지 기본값은 "브라우저 직접"입니다.
3. 콘텐츠 유형을 선택하세요; 사용할 수 있습니다 `application/octet-stream` 기본값으로.
4. 테스트할 파일 크기를 선택하세요.
5. 페이지는 1, 5, 8, 10, 12, 15, 20, 25 MB를 지원합니다.
6. 테스트 환경에서는 빠른 검증을 위해 먼저 1 MB를 선택할 수 있습니다.
7. 정식 성능 비교를 위해 여러 파일 크기를 선택하여 테스트하세요.

### 4.2 성능 테스트 시작

1. 스토리지 구성이 올바른지 확인하세요.
2. 적어도 하나의 파일 크기가 선택되었는지 확인하세요.
3. '성능 테스트 시작'을 클릭하세요.
4. 모든 파일 업로드가 완료될 때까지 기다리세요.
5. 평균 처리량, 최소 시간, 최대 시간을 확인하세요.
6. 각 파일 크기의 상태, 경과 시간, 처리량, 오류 메시지를 확인하세요.
7. 실패가 발생하면 먼저 브라우저 네트워크, 공용 엔드포인트, 교차 출처 구성, 객체 스토리지 상태를 확인하세요.

### 4.3 이번 테스트 결과

이 테스트는 1 MB 파일만 사용하여 경량 프론트엔드 직접 업로드 테스트를 수행합니다:

| 지표 | 결과 |
| --- | ---: |
| 파일 크기 | 1.0 MB |
| 상태 | 성공 |
| 시간 | 874 ms |
| 처리량 | 1.14 MB/s |
| 오류 메시지 | 없음 |

실제 결과: 업로드가 성공하였으며, 페이지가 경과 시간과 처리량 지표를 올바르게 생성할 수 있습니다.

> 성능 결과는 브라우저 네트워크, 클러스터 부하, 프록시 링크 및 객체 저장소 부하에 영향을 받을 수 있습니다. 단일 테스트는 기능적 가용성만 확인할 수 있으며, 공식적인 성능 수용은 동일한 환경에서 반복 테스트하고 통계를 기록해야 합니다. P50, P95, 그리고 실패율도 기록해야 합니다.

## 5. 주의사항
1. 테스트를 수행하기 전에 대상 버킷을 확인하여 테스트 파일이 잘못된 저장소 버킷에 작성되지 않도록 하십시오.
2. 문서나 스크린샷에 비밀 키를 일반 텍스트로 표시하지 마십시오.
3. 브라우저 직접 업로드는 퍼블릭 엔드포인트와 크로스-오리진 설정에 의존합니다.
4. S3-호환 서비스와 같은 MinIO 일반적으로 경로 스타일(Path Style)을 활성화해야 합니다.
5. 성능 테스트는 실 네트워크 트래픽과 저장소 기록을 생성하므로, 대용량 파일 테스트 전에 환경 영향을 평가하십시오.
6. 공식 성능 수용은 여러 차례 수행되어야 하며, 단일 브라우저 테스트 결과만으로는 충분하지 않습니다.
