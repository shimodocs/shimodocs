# 단일 노드 Kubernetes 배포

[← ShimoDocs Suite 배포 문서](../README.md)

## 1. 적용 가능한 시나리오
- **K8s 단일 노드 배포**:
    - 경량 소규모 팀, 200명 미만의 소규모 사용, PoC데모, 기능 검증 및 단기 테스트에 적합합니다.
- 서버는 1대만 필요하며, 서버가 설치 노드, K8s 마스터 노드, 비즈니스 워커 노드 역할을 동시에 수행합니다.
- **참고**
    - 공식 출시, 장기 운영 또는 이후 고가용성 확장을 위해서는 K8s 클러스터 배포를 사용하는 것이 권장됩니다.

## 2. 배포 프로세스 개요

| 단계 | 해야 할 일 | 완료 지표 |
| --- | --- | --- |
| 1. 시스템 환경 확인 | 서버 리소스, 디스크, 네트워크, 시간 동기화 및 기본 명령어 확인 | 서버가 배포 요건을 충족함 |
| 2. 설치 자료 준비 | 설치 프로그램과 제품 설치 패키지 확보; 오프라인 환경의 경우 오프라인 이미지 패키지도 준비 필요 | 파일 이름이 CPU 아키텍처와 일치함 |
| 3. 설치 자료 업로드 | 설치 프로그램과 설치 패키지를 배포 노드에 업로드 | 파일이 서버의 지정 디렉터리에 배치됨 |
| 4. 설치 프로그램 시작 | 웹 페이지 실행 `mdp-installer`  | 설치 페이지는 브라우저를 통해 접근할 수 있습니다 |
| 5. 웹 페이지 설치 | 배포 패키지를 선택하고, 노드를 구성하며, 환경 점검을 완료한 후 배포를 시작합니다 | 모든 설치 작업이 성공적으로 완료되었습니다 |
| 6. 설치 후 검수 | 클러스터, 서비스, 로그인, 라이선스 및 비즈니스 기능을 확인합니다 | 핵심 기능은 정상적으로 사용할 수 있습니다 |

## 3. 배포 전 준비

### 3.1 서버 정보 준비

| 정보 | 예시 | 설명 |
| --- | --- | --- |
| INSTALL_NODE_IP | `<INSTALL_NODE_IP>` | 단일 노드 K8s 배포는 1대의 서버만 사용합니다 |
| CPU 아키텍처 | `amd64` / `arm64` | 설치 프로그램과 설치 패키지는 서버 아키텍처와 일치해야 합니다 |
| 네트워크 환경 | 온라인 / 오프라인 | 공용 네트워크에 접근 가능하면 온라인을 선택하고, 내부 또는 격리 환경이면 오프라인을 선택합니다 |
| 실행 사용자 | `root` 또는 권한이 있는 사용자 `sudo` 권한 | 설치 프로그램은 배포 작업을 실행하기 위해 필요합니다 SSH |
| SSH 포트 | `22` | 만약 SSH 포트가 변경되었으며, 실제 포트를 입력하십시오. |
| 접속 프로토콜 | HTTP / HTTPS | HTTP 테스트 환경에 사용할 수 있습니다; HTTPS 운영 또는 외부 접근에는 추천됩니다. |
| ACCESS_DOMAIN | `<ACCESS_DOMAIN>` 또는 `<INSTALL_NODE_IP>` | 사용자가 접근할 진입 주소 ShimoDocs Suite |
| 데이터 디렉터리 | `/data` | 별도의 데이터 디스크 마운트 사용을 추천합니다. |

### 3.2 설치 자료 준비

| 자료 | 예시 파일 이름 | 설명 |
| --- | --- | --- |
| 설치 프로그램 | `mdp-installer-amd64` | 예시 용도 `amd64` 아키텍처; 다른 아키텍처의 경우 실제 파일 이름으로 교체 |
| 제품 설치 패키지 | `co1.8.20260807.3639-drive-release..tar.gz` | 단일 노드 K8s 배포의 경우, 파일 이름에 포함되지 않은 배포 패키지를 선택합니다. `k3s`; 파일 이름은 실제 전달된 내용 기준 |
| 기본 오프라인 이미지 패키지 | `smbase_image-amd64.tar.gz` | 오프라인 설치에만 필요합니다 |
| 제품 오프라인 이미지 패키지 | `offline_app_image.tar.gz` | 오프라인 설치에만 필요하며, 제품 설치 패키지 버전과 일치해야 합니다. |

참고:

- 명령어 내 파일 이름은 실제 파일 이름으로 교체해야 합니다. 예: `mdp-installer-amd64`, `co1.8.<VERSION>-drive-release.tar.gz`.
- 제품 설치 패키지, 오프라인 이미지 패키지, 서버 CPU 아키텍처는 일치해야 합니다.
- 오프라인 설치 전에, 배포 중 패키지를 임시로 추가하지 않도록 기본 오프라인 이미지 패키지와 제품 오프라인 이미지 패키지를 한 번에 준비하는 것이 좋습니다.

### 3.3 서버 자원 확인

| 항목 | 권장 요구 사항 |
| --- | --- |
| 서버 수 | 1 |
| CPU | 16코어 이상 |
| 메모리 | 32GB 이상 |
| 시스템 디스크 | 루트 `/` 파티션 100GB 이상 |
| 데이터 디스크 | 독립적으로 마운트 `/data`공간 300GB 이상 |
| 오프라인 설치 | 이미지 패키지와 임시 추출 파일을 위해 데이터 디스크에 100GB 이상 추가로 확보하는 것이 좋습니다. |

서버에서 실행: 

```bash
lscpu
free -g
df -h
timedatectl status
```

다음 결과 확인: 

- CPU, 메모리, 디스크가 배포 사양을 충족하는지. 
- `/data` 별도의 데이터 디스크에 마운트되었습니다. 
- 시스템 시간 동기화는 정상입니다. 
- 서버에 다음을 통해 접속할 수 있습니다 SSH 로그인. 
- 온라인 설치 환경은 공용 네트워크에 접근할 수 있으며, 오프라인 설치 환경은 준비된 오프라인 이미지 패키지를 사용합니다. 

### 3.4 포트 확인 

| 포트 | 목적 | 
| --- | --- | 
| `22/TCP` | SSH 로그인 및 설치 작업 실행 | 
| `18080/TCP` | 설치 관리자 웹 페이지 | 
| `80/TCP` 또는 `443/TCP` | ShimoDocs Suite 접근 경로 | 

서버에 방화벽 또는 보안 그룹이 활성화되어 있는 경우, 위의 포트를 사전에 열어 주십시오. 

## 4. 설치 도구 및 패키지 업로드 

다음 예시는 `amd64` 아키텍처를 사용합니다. 다른 아키텍처의 경우 실제 파일 이름으로 교체하십시오. 

### 4.1 설치 관리자 업로드 

로컬 컴퓨터에서 실행: 

```bash
scp mdp-installer-amd64 root@<INSTALL_NODE_IP>:/root/
```

### 4.2 오프라인 이미지 패키지 업로드

이 단계는 온라인 설치의 경우 생략할 수 있습니다.

오프라인 설치의 경우, 오프라인 이미지 패키지를 배포 노드에 업로드해야 합니다:

```bash
scp smbase_image-amd64.tar.gz offline_app_image.tar.gz root@<INSTALL_NODE_IP>:/root/
```

### 4.3 서버 로그인

```bash
ssh root@<INSTALL_NODE_IP>
```

### 4.4 설치 프로그램에 실행 권한 추가

```bash
chmod +x /root/mdp-installer-amd64
```

### 4.5 설치 프로그램 웹 페이지 실행

서버에서 실행:

```bash
cd /root
./mdp-installer-amd64 server
```

설치 프로그램을 백그라운드에서 실행하려면 다음을 사용할 수 있습니다: 

```bash
nohup /root/mdp-installer-amd64 server > /root/mdp-installer.log 2>&1 &
```

브라우저 접근: 

```text
http://<INSTALL_NODE_IP>:18080
```

## 5. 웹 페이지를 통한 설치

### 5.1 배포 패키지 선택

설치 프로그램 웹 페이지에 접속한 후 이번에 배포할 제품 배포 패키지를 선택합니다.

 K8s 단일 노드 배포인 경우 파일 이름에 포함되지 않은 배포 패키지를 선택하세요 `k3s`예를 들어:

```text
co1.8.20260807.3639-drive-release.tar.gz
```

### 5.2 구성 SSH 연결

설치 프로그램은 배포 노드에 로그인합니다 SSH 설치 작업을 실행합니다. SSH 설정은 두 가지 인증 방법을 지원합니다:

- 개인 키 인증.
- PASSWORD 인증.

사용하는 것을 권장합니다 `root` 배포를 수행할 권한이 있는 사용자 또는 사용자. `sudo` 정보를 입력한 후, 먼저 연결을 테스트하여 설치 관리자가 배포 노드에 정상적으로 로그인할 수 있는지 확인할 수 있습니다.

### 5.3 기본 구성 확인

배포 패키지를 선택한 후 다음 단계로 진행합니다. 특별한 요구 사항이 없는 경우 페이지의 기본 구성을 유지할 수 있습니다; 배포 환경에 이미 도메인 이름, 인증서, 네트워크 구간 또는 미들웨어에 대한 명확한 계획이 있는 경우 실제 계획에 따라 입력하십시오.

구성 중 확인할 핵심 사항: 

- 접근 프로토콜과 ACCESS_DOMAIN 가 올바르게 입력되었는지 확인합니다. 
- Pod CIDR 및 서비스 CIDR 기존 네트워크, 사무실 네트워크, VPN, 또는 IDC 네트워크 구간. 
- 데이터 디렉토리로 `/data` 또는 실제 계획된 데이터 디스크 디렉토리를 사용합니다. 
- 온라인/오프라인 설치 방법이 현재 네트워크 환경과 일치하는지 확인합니다. 

### 5.4 초기 배포 

구성이 완료되면 초기 배포를 클릭합니다. 페이지에 이번 배포 개요가 표시됩니다. 다음 사항을 확인하십시오: 

- 제품 패키지 버전. 
- 배포 NODE_IP. 
- SSH 사용자 및 포트. 
- ACCESS_DOMAIN 및 프로토콜. 
- 데이터 디렉토리. 
- 온라인 또는 오프라인 설치 모드. 
- 미들웨어 선택. 

모든 사항이 올바른지 확인한 후 계속합니다. 

### 5.5 시스템 환경 확인

설치 프로그램이 서버 환경을 자동으로 점검합니다.

체크를 통과한 후 배포를 계속합니다. 실패한 항목이 있는 경우 페이지 안내에 따라 처리하고 재확인하십시오. 일반적인 처리 방법은 다음과 같습니다: 

- 디스크 공간 부족: 공간을 정리하거나 데이터 디스크를 확장합니다. 
- 포트 사용 불가: 포트를 해제하거나 포트 사용을 조정합니다. 
- SSH 연결 실패: 계정을 확인하고, PASSWORD, 개인 키, 포트 및 보안 그룹. 
- 시간 동기화 이상: 설정 NTP 또는 서버 시간을 보정합니다. 
- 기본 명령이 없음: 시스템 배포판에 따라 누락된 명령을 설치합니다. 

### 5.6 배포 시작 

환경 검사가 통과되면 클릭하여 배포를 시작합니다. 

배포 과정에서 각 구성 요소의 실행 로그를 확인할 수 있습니다. 설치 중에는 다음 사항을 확인하십시오: 

- 설치 프로그램 프로세스가 실행 중이어야 합니다. 
- 브라우저가 설치 노드 네트워크에 연결될 수 있는지 확인합니다. 
- 서버를 재시작하지 마십시오. 
- 설치 패키지, 오프라인 이미지 패키지 또는 데이터 디렉터리를 이동하거나 삭제하지 마십시오. 

### 5.7 설치 완료 대기

설치 과정에는 시간이 필요하며, 구체적인 시간은 서버 성능, 네트워크 환경 및 이미지 다운로드 속도에 따라 다릅니다.

페이지에 모든 작업이 성공적으로 실행되었고 실패한 구성요소가 없는 경우, 배포가 완료되었음을 나타냅니다.

### 5.8 설치 결과 확인

설치가 완료되면 설치 프로그램은 배포 완료 페이지와 접근 정보를 표시합니다. 비즈니스 시스템과 MDP 운영 플랫폼.

비즈니스 주소 방문: 

```text
http://<ACCESS_DOMAIN>/
```

설치 중 HTTPS 가 구성된 경우, 다음을 방문하십시오: 

```text
https://<ACCESS_DOMAIN>/
```

기본 계정 또는 관리자 계정으로 로그인 후, 초기 설정을 즉시 변경하십시오. PASSWORD 즉시 변경

접속 MDP 운영 플랫폼에 접근하기 전에 페이지에 실패한 작업이 없는지 먼저 확인하십시오. 

```text
http://<ACCESS_DOMAIN>/mdp/
```

관리자를 수정해야 하는 경우, 배포 노드에서 다음 명령을 실행하여 수정하거나 재설정할 수 있습니다. MDP 관리자 PASSWORD다음 명령을 배포 노드에서 실행하여 수정하거나 재설정할 수 있습니다. PASSWORD.
{password}를 새로운 복잡하고 강력한 암호로 교체하십시오. PASSWORD 실제 보안 요구 사항에 따라 적용하십시오.

```bash
kubectl exec -it $(kubectl get pods -l app=mdp -o jsonpath='{.items[0].metadata.name}') -- reset-admin-password {password}
```

## 6. 설치 후 검수

### 6.1 확인 K8s 노드 상태

배포 노드에서 실행:

```bash
kubectl get node
```

노드 상태는 다음과 같아야 합니다 `Ready`. 

서비스를 계속 확인하십시오: 

```bash
kubectl get pod -A
```

정상 상태는 일반적으로 다음과 같습니다: 

- `Running`: 서비스가 실행 중입니다. 
- `Completed`: 작업이 실행을 완료했습니다. 

다음과 같은 상태가 나타나면 `CrashLoopBackOff`, `ImagePullBackOff`, `Error`, `Pending`먼저 해당 Pod 로그를 확인하고 처리하십시오. 

### 6.2 접근 경로 확인 

접속 ShimoDocs Suite 브라우저를 통한 접근: 

```text
http://<ACCESS_DOMAIN>/
```

설치 중 HTTPS 가 구성되었습니다. 방문하십시오: 

```text
https://<ACCESS_DOMAIN>/
```

로그인 페이지가 정상적으로 열리는지 확인합니다.

### 6.3 관리 백엔드 및 라이선스 확인

다음 항목을 확인합니다:

- 관리자 백엔드에 접근할 수 있는지
- 관리자가 로그인할 수 있는지
- 라이선스 페이지를 열 수 있는지
- 기계 정보를 확인할 수 있습니다.
- 승인 절차에 따라 라이선스를 신청하거나 업데이트할 수 있습니다.

## 7. 일반적인 문제 해결

### 7.1 브라우저가 설치 페이지를 열 수 없음

다음을 확인하십시오:

- 설치 프로그램 프로세스가 여전히 실행 중인지 여부
- 포트 `18080` 가 방화벽 또는 보안 그룹에 의해 차단되었는지 여부
- 브라우저가 접근하는 IP가 INSTALL_NODE_IP.

서버에서 다음을 실행할 수 있습니다:

```bash
ps -ef | grep mdp-installer | grep -v grep
ss -lntp | grep 18080
```

### 7.2 환경 점검 실패

페이지의 안내에 따라 각 항목을 처리하세요. 처리 후 설치 프로그램 페이지로 돌아가 환경 검사를 다시 실행하십시오.

우선 순위 확인:

- 여부 CPU, 메모리 및 디스크가 요구 사항을 충족합니다.
- 여부 `/data` 은 독립형 데이터 디스크입니다.
- 서버 시간이 동기화되어 있는지 여부.
- 여부 SSH 사용자에게 배포 권한이 있습니다.

### 7.3 오프라인 설치 이미지 가져오기 실패

지침 확인:

- 오프라인 이미지 패키지가 배포 노드에 업로드되었는지 여부.
- 기본 오프라인 이미지 패키지와 제품 오프라인 이미지 패키지가 완전한지 여부.
- 이미지 패키지 버전이 제품 설치 패키지와 일치하는지 여부.
- 개인 이미지 저장소 주소, 계정 및 PASSWORD 이 올바르게 작성되어 있는지 확인하십시오.

### 7.4 Pod이 장시간 비정상 상태로 남음

먼저, 비정상 Pod를 확인:

```bash
kubectl get pod -A
```

로그를 다시 확인: 

```bash
kubectl logs -n <namespace> <pod-name>
```

로그를 기반으로 이미지, 구성, 리소스 또는 종속성과 관련된 문제 처리.
