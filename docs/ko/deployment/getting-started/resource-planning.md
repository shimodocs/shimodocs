# 리소스 계획

[← ShimoDocs Suite 배포 문서](../README.md)

## 1. 문서 목적

이 문서는 사유화 배포 시나리오에서 서버 및 미들웨어 자원 계획을 안내하기 위해 사용되며, 구현 엔지니어, 운영 엔지니어, 사전영업 기술 지원 담당자가 참고할 수 있습니다.

문서의 내용은 과거 프로젝트 용량 계획, 샘플 구성, 미들웨어 기준을 기반으로 하며, 사전영업 견적, 자원 신청, 구현 배포, 이후 확장 평가에 사용할 수 있습니다.

## 2. 범위 및 지침

### 2.1 범위

이 문서는 사유화 배포 시나리오에서 다양한 사용자 규모에 따른 애플리케이션 노드 및 미들웨어 자원의 사전 계획에 적용됩니다.

### 2.2 지침

* 이 문서에 있는 구성은 모두 권장 구성으로, 초기 단계 프로젝트 용량 평가 및 자원 계획에 사용됩니다.

* 애플리케이션 노드 자원과 미들웨어 자원은 별도로 계산해야 하며, 혼합 계획은 권장되지 않습니다.

* 대규모 사용자 시나리오에서는 피크 비즈니스 부하, 동시성 모델, 용량 스트레스 테스트 결과 및 운영 모니터링 데이터를 기반으로 미들웨어 자원을 추가로 조정해야 합니다.

* 정식 운영 환경에서는 확장 용량을 예약하고 고가용성 구축을 우선하는 것이 권장됩니다.

* 국산 아키텍처 서버를 사용하는 경우, CPU 전체 자원을 표준 사양의 두 배로 추정하는 것이 권장됩니다.

## 3. 계획 원칙

### 3.1 애플리케이션 및 미들웨어 배포 원칙

* 사용자가 10,000명 미만인 시나리오에서는 일부 미들웨어를 배포할지 평가할 수 있습니다. K8s 실제 프로젝트 상황을 기반으로 한 클러스터.

* 사용자가 10,000명 이상인 시나리오에서는 애플리케이션 노드와 미들웨어를 완전히 분리하여 배포하는 것이 권장됩니다.

* 데이터베이스, 캐시, 메시지 큐, 검색 서비스와 같은 핵심 미들웨어는 우선 고가용성 아키텍처로 배포하는 것이 권장됩니다.

* 조건이 허락될 경우, 안정성 및 유지보수성을 향상시키기 위해 성숙한 퍼블릭 클라우드 관리형 미들웨어 서비스를 우선적으로 사용하는 것이 권장됩니다.

### 3.2 객체 스토리지 계획 원칙

* 가능하면 Alibaba Cloud와 같은 퍼블릭 클라우드 객체 스토리지 서비스를 사용합니다. OSSHuawei Cloud, OBSTencent Cloud COS, AWS S3.

* 객체 스토리지를 사설로 배포하는 경우, SSD 디스크를 사용해야 하며, 용량 확장 후의 성능, 안정성 및 운용성을 신중하게 평가해야 합니다.

* 비즈니스가 대용량 파일 업로드, 다운로드, 미리보기 또는 다중 사용자 협업 대형 스프레드시트 편집 시나리오와 관련된 경우, 독립적인 객체 스토리지 서비스를 우선 사용하는 것이 권장됩니다.

## 4. 애플리케이션 노드 계획

### 4.1 애플리케이션 노드 사양 구분

#### 사양 A

* 권장 사양: `24C / 48G / >=500G SSD * N`

* 적용 범위: 10,000명 미만 사용자

* 적용 기능: 

   * 중소기업 시나리오를 지원할 수 있음 

   * 미들웨어는 프로젝트에 따라 K8s 환경에 배포될 수 있음 

   * 단일 노드에 부하가 많이 걸리며, 노드가 장애가 발생할 경우 영향 범위가 비교적 큼 

#### 사양 B 

* 권장 사양: `16C / 32G / >=300G SSD * N` 

* 적용 범위: 10,000명 이상 사용자 

* 적용 기능: 

   * 대규모, 고가용성 배포 시나리오에 적합 

   * 독립 미들웨어 사용 필수 

   * 소규모 사양 다중 노드 방식을 사용하여 더 균형 잡힌 스케줄링과 유연한 확장을 제공 

   * 노드 유지보수 또는 문제 발생 시 전체 비즈니스 영향이 더 적음 






### 4.2 애플리케이션 노드 계산 기준 

기존 프로젝트 사례 및 용량 계산 규칙을 기반으로 애플리케이션 노드는 다음 공식으로 추정하는 것이 권장됩니다: 

`Number of nodes = Number of users × 0.03 ÷ 160` 

간단히 이해하면: 

`Number of nodes ≈ Number of users ÷ 5300`

여기서:

* 동시 사용자 계수는 다음과 같이 추정됨 `0.03`.

* 단일 노드의 용량은 대략 `16C / 32G` 다음과 같음 `150 ~ 180 QPS`.

* 계산 기준으로 사용하는 것이 권장됨 `160 QPS/node` 다음과 같습니다.

* 계산된 결과는 반올림하여 사용하고, 추가적인 확장용 용량을 확보하는 것이 권장됩니다.

## 5. 미들웨어 계획

### 5.1 미들웨어 분류 원칙

현재 미들웨어 리소스 계획은 두 가지 기준 계층에 따라 실행됩니다:

* `Users below 3,000`: 소규모 기준 구성 사용.

* `3000 users and above`: 대규모 기준 구성 사용. 

10,000, 30,000, 50,000, 100,000, 200,000, 300,000, 500,000, 700,000 사용자와 같은 대규모 시나리오의 경우, '3,000 사용자 이상' 기준 구성부터 균일하게 시작하고, 비즈니스 성장에 따라 동적으로 확장하는 것이 권장됩니다.

## 6. 구현 및 운영 & 유지보수 제안

### 6.1 배포 구현 제안

* MySQL, MongoDB, Redis, Kafka, Elasticsearch 고가용성 클러스터 모드로 배포하는 것이 권장됩니다.

* 조건이 허용된다면 안정성과 유지보수성 향상을 위해 공용 클라우드 관리형 데이터베이스와 미들웨어 서비스를 우선적으로 사용하는 것이 권장됩니다.

* 10,000명 이상의 사용자가 있는 사용자 시나리오에서는 애플리케이션 노드와 미들웨어를 별도로 배포하는 것이 권장됩니다. 

*  Kafka의 경우, 다른 비즈니스와 리소스를 공유하지 않도록 별도의 인스턴스를 사용하는 것이 권장됩니다. 

### 6.2 객체 스토리지 구현 권장 

* 공용 클라우드 객체 스토리지 제품을 우선적으로 사용하는 것이 권장됩니다. 

* 사설 객체 스토리지를 사용하는 경우, SSD 디스크를 사용해야 합니다. 

* 팀 공간이 대규모 파일 업로드, 다운로드 또는 미리보기 시나리오를 포함하는 경우, 객체 저장 용량, 처리량, 대역폭이 주요 평가 요소가 되어야 합니다. 

### 6.3 확장 고려사항 

다음 비즈니스 시나리오에서는 미들웨어 리소스 평가 및 추가를 우선순위로 하는 것이 권장됩니다: 

* 대량의 첨부파일 업로드, 다운로드 또는 미리보기 

* 고빈도 전체 텍스트 검색 

* 메시지 누적 또는 집중적인 비동기 작업 

* 피크 기간 동안의 배치 쓰기 및 통계 분석 

* 로그 볼륨 지속적 증가 

중점적으로 봐야 할 주요 지표는 다음과 같습니다: 

* 데이터베이스: CPU메모리, 디스크 IO 

* Redis: 연결 수, 히트율, 대역폭 사용량 

* Kafka: 브로커 수, 메시지 누적, 디스크 공간 

* Elasticsearch: 노드 수, 인덱스 크기, 저장 용량 

* 오브젝트 스토리지: 읽기/쓰기 성능, 요청 처리량, 용량, 대역폭 






## 7. 결론 

* 소규모 시나리오(사용자 10,000명 미만)에서는 사양 A의 애플리케이션 노드 구성을 사용하는 것을 권장하며, 프로젝트 상황에 따라 클러스터 내 일부 미들웨어 배포 여부를 평가한다. 

* 중대형 시나리오(사용자 10,000명 이상)에서는 사양 B의 애플리케이션 노드 구성을 사용하고, 독립 미들웨어 및 고가용성 아키텍처와 함께 사용하는 것을 권장한다. 
* 미들웨어는 두 가지 기준에 따라 구성하는 것이 권장된다: "3,000명 이하"와 "3,000명 이상". 대규모 프로젝트의 경우, 지속적인 확장은 스트레스 테스트 및 모니터링 데이터를 기반으로 진행한다. 
* 공식 구현 전에, 배포 사양과 실제 지원 범위의 불일치를 방지하기 위해 자원 계획 확인, 호환성 검증, 용량 스트레스 테스트를 동시에 완료해야 한다. 

* 국내를 사용하는 경우 CPU 아키텍처 서버의 경우, 표준 사양의 두 배로 자원을 추정하는 것이 권장됩니다. 

* 이 매뉴얼은 사전 설치 선택을 위한 것이며, 현장 부하 테스트나 최종 구현을 대체하지 않습니다.
